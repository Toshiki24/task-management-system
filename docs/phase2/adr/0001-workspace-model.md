# ADR 0001: ワークスペース方式の採用（マルチテナントは採用しない）

- ステータス: 承認（Accepted）
- 日付: 2026-10-05
- 関連: [Phase 2 要件定義](../requirements.md) §3・§4

## コンテキスト

Phase 2 では、社内の**チーム/部署単位で可視性・権限を分けて**運用したいという要件がある。一方で本システムは**自社で運用する社内ツール**を前提とし、**1 つのインスタンスを 1 つの組織（＝自社）が運用**する。複数の会社を 1 インスタンスで分離してホスティングする要件（SaaS 併売・受託ホスティング等）は現時点で無い。

この「組織内の分離」をどう実現するか、次の 3 案を検討した。

| 案 | 内容 | 上位境界が分けるもの |
| --- | --- | --- |
| (a) フラット | 組織内に区切りを設けず、プロジェクト＋メンバー＋ロールのみ | （区切り無し） |
| (b) ワークスペース | 組織内を「ワークスペース（チーム/部署）」で分け、可視性・権限の境界にする | 社内のチーム/部署 |
| (c) フルマルチテナント | 1 インスタンスで複数の**会社**を完全分離する | 会社（テナント） |

## 決定

**(b) ワークスペース方式を採用する。**

- **1 インスタンス = 1 組織（自社）** の単一構成とし、会社間を分離する多組織分離（マルチテナント）は行わない。
- 組織内を **ワークスペース（チーム/部署）** で分け、ワークスペースを**可視性と権限の境界**にする。
- データは**共有 DB**とし、プロジェクトに `workspace_id` を持たせてワークスペースに属させる（タスク・コメント等はプロジェクトを通じて所属）。可視性・認可はこの所属とロールで制御する。
- ロールは**3 スコープ**に分離する。

| スコープ | ロール |
| --- | --- |
| システム全体 | System Admin |
| ワークスペース内 | Admin / Member / Viewer |
| プロジェクト内 | OWNER / MEMBER（既存 `ProjectAccess` を拡張） |

## 検討した代替案

### (a) フラット — 不採用
実装は最も軽いが、**チーム/部署単位の可視性分離ができない**。中〜大規模の社内利用では「他部署のプロジェクトを見せたくない」という基本要件を満たせない。

### (c) フルマルチテナント — 不採用
会社間を 1 インスタンスで完全分離する方式。自社運用（会社ごとにインスタンスを建てる）前提では、**アプリ内で会社間分離を保証する意味が薄く、過剰設計**になる。全テーブルへのテナント識別子の付与、分離の保証、クロステナントの分離テスト等、**実装・テストのコストが重い**。SaaS 併売・受託ホスティングの予定が無いため、現時点では採用しない。

## 結果（影響とトレードオフ）

### 良い点
- 要件（チーム/部署の可視性分離）に対して**必要十分**で、実装・テストが現実的。
- 既存の `ProjectAccess`（認可の集約）を**ワークスペース対応に拡張**しやすい。
- 将来、会社間分離が必要になった場合は、**ワークスペースを上位概念（組織/テナント）へ拡張**する道が残る。

### 注意点・トレードオフ
- **会社間分離は提供しない。** 将来 SaaS 併売や「1 台で複数クライアント」を行う場合は (c) への再設計が必要（本 ADR を Superseded にして改訂する）。
- `workspace_id` を**データモデルと認可に一貫して通す**必要がある（プロジェクト→タスク/コメント等へ波及）。可視性フィルタ（所属ワークスペースのみ表示）を**取りこぼし無く**適用することが重要。
- System Admin は運用上フルアクセスを持つため、**操作を監査ログに記録**する（要件 §3）。

## 波及する変更（概要）

詳細は M1 の基本設計で定義する。

- テーブル追加：`workspaces`、`workspace_members`（ロール付き）
- 既存テーブル変更：`projects` に `workspace_id` を追加
- 認可の 3 層化：システム（横断）／ワークスペース（所属＋ロール）／プロジェクト（既存）
- 可視性制御：所属していないワークスペースのプロジェクトは既定で返さない
