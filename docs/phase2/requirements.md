## 1. 背景と目的

Phase 1 で「要件→設計→実装→照合→テスト→セキュリティ見直し→AWS 構築→本番デプロイ」の一連を完了した。機能は基本的なプロジェクト/タスク管理に留まっている。

Phase 2 では、**開発チームが実際の業務で使える水準**に引き上げる。具体的には次を目指す。

- 社内のチーム/部署単位で**可視性と権限を分けて**運用できるようにする
- 開発チームが**日常的に使える UX**（ボード・検索・通知・リアルタイム等）を備える
- **Git（GitHub / GitLab / self-managed GitLab）と連携**し、ブランチや PR/MR の状態からタスクが自動で動くようにする（手作業のステータス更新を減らす）
- **自社インフラ（自社 AWS / オンプレ）で運用できる**形にする

本システムは**自社で運用するチーム向けの社内ツール**を想定する（1 つのインスタンスを 1 つの組織＝自社が運用する）。

---

## 2. このシステムの特徴（ねらい）

| 特徴 | 内容 |
| --- | --- |
| **Git と一体** | ブランチ/PR/MR/パイプラインの状態でタスクが自動遷移。タスクとコミット/PR を双方向にリンクし、手作業のステータス更新を減らす。 |
| **自社運用** | 自社 AWS もしくはオンプレに設置して運用でき、データを自社で保有できる。 |
| **チーム単位の分離** | 社内のチーム/部署を「ワークスペース」として分け、可視性・権限を分離する。 |
| **開発の見える化** | Git とタスクのデータから開発の状況（進捗・リードタイム等）を可視化する。 |

## 3. 利用者とロール

### 想定利用者

| 利用者 | 役割 | 主なニーズ |
| --- | --- | --- |
| 開発メンバー | コードを書く人 | 手でステータス更新したくない。Git 操作が反映されてほしい。速い UX。 |
| チームリード | チームの管理 | 進捗・負荷・ボトルネックの把握。メンバー管理。 |
| システム運用者 | インスタンスの運用 | 全体の管理、Git 接続設定、SSO/バックアップ、監査、アップグレード。 |

### ロール（3 スコープ）

ロールは**スコープ（管理範囲）ごとに分離**する。システム運用はチームを横断する別次元のため、ワークスペース内ロールと同一視しない。

| スコープ | ロール | 権限の概要 |
| --- | --- | --- |
| **システム全体** | **System Admin** | インスタンス全体の運用：全ワークスペース・全ユーザーの管理、Git 接続・SSO・システム設定、監査ログ閲覧、バックアップ。 |
| **ワークスペース内** | **Admin** | ワークスペース設定、メンバー招待/削除、ロール付与 |
| | **Member** | プロジェクト/タスクの作成・編集 |
| | **Viewer** | 閲覧のみ |
| **プロジェクト内** | **OWNER / MEMBER** | 既存のプロジェクト単位の権限（Phase 1 の `ProjectAccess` を拡張。ワークスペースロールの下にぶら下げる） |

**System Admin のアクセス方針**：自社運用（データを自社で保有）が前提のため、System Admin は運用に必要な範囲でフルアクセスを持つ。ただし**操作を監査ログに記録**する。

## 4. ワークスペース/チーム構造

- **1 インスタンス = 1 組織（自社）** の単一構成とする。組織（会社）同士を 1 インスタンスで分離する多組織分離（マルチテナント）は**行わない**。
- 組織の中を **ワークスペース（チーム/部署）** で分ける。ワークスペースが**可視性と権限の境界**になる。
- **プロジェクトはいずれかのワークスペースに属する**。タスク・コメント等はプロジェクトを通じてワークスペースに属する。
- メンバーはワークスペースに所属し、ワークスペース内ロール（Admin/Member/Viewer）を持つ。
- **可視性**：所属していないワークスペースのプロジェクトは既定で見えない。System Admin は全体を管理できる。
- 既存の運用データは無い前提とし、データ移行は行わない。

> 方式の決定は `docs/phase2/adr/0001-workspace-model.md`（別途作成）に記録する。

## 5. 機能要件

### 5.1 認証・アカウント
- ログイン（Phase 1 の BFF＋暗号化 Cookie＋リフレッシュトークンを踏襲）
- **招待（メール招待トークン：期限・ワンタイム）＋ロール指定**
- **ユーザー追加 API**（招待フローの一部。実行できるのは System Admin / ワークスペース Admin）
- MFA（多要素認証）
- SSO（SAML/OIDC）※将来の SCIM プロビジョニングを見据えた設計

### 5.2 ワークスペース/チーム管理
- ワークスペースの作成・編集・アーカイブ
- メンバーの招待・追加・削除・ロール変更
- ワークスペース単位の設定（Git 接続、通知既定、ワークフロー既定 等）

### 5.3 プロジェクト管理
- 一覧・作成・詳細・編集・削除（Phase 1 を踏襲しワークスペース配下に）
- プロジェクトメンバー（OWNER/MEMBER）
- プロジェクト設定（ワークフロー、連携リポジトリ 等）

### 5.4 タスク管理
- 一覧・作成・詳細・編集・削除（担当者・優先度・期限）
- **カスタムワークフロー**：状態（カラム）をワークスペース/プロジェクトで定義できる（固定の TODO/IN_PROGRESS/DONE に縛られない）
- **サブタスク／チェックリスト**
- **タスク依存**（ブロック/被ブロック）
- ラベル、見積（ポイント）
- 一括操作（状態・担当・ラベルの一括変更）

### 5.5 ボード/ビュー
- **カンバンボード（状態列×ドラッグ&ドロップ）**
- リストビュー
- **検索・絞り込み・並べ替え＋保存ビュー**（担当者/状態/優先度/期限/ラベル/キーワード）
- **My Tasks**（自分の担当・期限間近・期限超過）
- ページネーション

### 5.6 コラボレーション
- コメント（Markdown、編集/削除、**@メンション**）
- ウォッチャー（フォロー）
- 添付ファイル（S3 もしくは自己ホスト時はオブジェクトストレージ/ボリューム）
- アクティビティ履歴（誰がいつ何を変えたか。Phase 1 の `TaskStatusHistory` を発展）
- **通知**：アプリ内／メール（担当にされた・メンション・期限が近い・状態変更 等）
- **リアルタイム更新**（複数人が同じ画面で即時反映）

### 5.7 Git 連携
- [7. Git 連携要件](#7-git-連携要件) を参照

### 5.8 見える化・ダッシュボード
- 進捗（状態別件数・完了率）、担当別の負荷、期限超過
- **開発指標**（サイクルタイム、スループット、リードタイム 等。Git × タスクのデータから算出）

### 5.9 管理・監査
- System Admin 向け管理（ワークスペース・ユーザー・Git 接続・システム設定）
- **監査ログ**（重要操作の記録・閲覧）
- データのインポート/エクスポート（CSV 等。他ツールからの移行・バックアップ）

## 6. UX 要件

開発者が日常的に快適に使えることを重視する。

| 項目 | 要件 |
| --- | --- |
| **速さ・操作性** | キーボード操作、**コマンドパレット（Cmd/Ctrl+K）**、楽観的更新（操作の即時反映） |
| **カンバン** | ドラッグ&ドロップで状態変更、カード上で主要情報を把握 |
| **検索/ビュー** | 絞り込み条件を**保存ビュー**として再利用、URL で共有 |
| **表示** | **ダークモード**、レスポンシブ（スマホ/タブレット）、日時は利用者のタイムゾーン（既定 JST） |
| **アクセシビリティ** | キーボードだけで主要操作ができる、十分な文字コントラスト、画面読み上げソフトへの対応（視覚に障害のある人も使える配慮） |
| **空状態・オンボーディング** | 初回利用時のガイド、空のときの案内、デモデータ |
| **国際化（i18n）** | 文言の外部化（日本語／英語を想定） |
| **フィードバック** | ローディング/エラー/成功の明確な表示、破壊的操作の確認 |
| **通知 UX** | アプリ内の通知センター（既読/未読）、通知の種類ごとの ON/OFF 設定 |

## 7. Git 連携要件

- **プロバイダ抽象化（`IGitProvider`）**：GitHub / GitLab の差異（Webhook 署名方式・API・認証）をアダプタで吸収する
- **対応プロバイダ**：GitHub、GitLab（gitlab.com）、**self-managed GitLab（オンプレ）**。接続先はベース URL を設定可能にする
- **プライベートリポジトリ対応**（企業利用の前提）：
  - GitHub は **GitHub App**（インストール単位の短命トークン・最小権限・個人非依存）を推奨。代替で OAuth/PAT
  - GitLab は **Project/Group アクセストークン**または OAuth（オンプレはベース URL＋トークン）
  - 資格情報は**シークレットストアに保管**（AWS: Secrets Manager、オンプレ: 外部シークレット）。**DB 平文に置かない**
  - 権限は**最小**（読み取り中心＋双方向操作に必要な分）。**ワークスペース単位で資格情報を分離**
- **タスク自動遷移**：ブランチ作成→進行中、PR/MR 作成→レビュー中、マージ→完了。**遷移ルールはワークスペース/プロジェクト単位で設定可能**
- **双方向リンク**：タスクからブランチ/PR 作成、`Closes #123` 等でタスク自動クローズ、タスクのタイムラインにコミット/PR/パイプライン結果を表示
- **identity マッピング**：Git ユーザー（GitHub/GitLab）とアプリのメンバーを対応付け、活動を正しく帰属させる
- **Webhook**：署名検証・冪等処理・イベント駆動で受け取る（再送・順序入れ替わりに耐える）

## 8. 運用形態

自社で運用できるよう、2 系統の設置方法を用意する。

| 形態 | 用途 | 内容 |
| --- | --- | --- |
| **AWS（Terraform）** | 自社 AWS に構築 | Phase 1 の Terraform をモジュール化し、`terraform apply` で構築 |
| **自己ホスト（Docker Compose / Helm）** | オンプレ・任意環境 | アプリ＋DB を同梱したコンテナ構成で、AWS 非依存に起動できる |

いずれも、設定は環境変数、秘密情報は外部シークレット、ヘルスチェック・マイグレーション手順・バックアップ/リストア手順・アップグレード手順を整備する。

## 9. 非機能要件

| 分類 | 要件 |
| --- | --- |
| **セキュリティ** | ワークスペース境界での可視性制御、認可の集約と自動テストでの担保、監査ログ、MFA、SSO、Git 資格情報の安全な保管、Phase 1 のセキュリティ対策（BFF・CSP nonce・レート制限・最小権限 等）を維持 |
| **可観測性** | 構造化ログ、主要メトリクス、分散トレース、アラート。運用者が状態を把握できること |
| **性能/拡張** | Lambda + RDS の接続枯渇対策（RDS Proxy 等の検討）、ページネーション、一覧取得時に DB への問い合わせが無駄に増えないようにする（N+1 問題の回避）、リアルタイム通信のスケール方針 |
| **テスト** | 既存の UT/API/結合/画面/システム/セキュリティ方針を踏襲。ワークスペースの可視性・認可は重点的にテスト |
| **運用** | マイグレーション・バックアップ/リストア・アップグレード手順の文書化、設定の外部化 |

## 10. スコープ（マイルストーン）

各マイルストーンは**単体で完成・デモ可能**な単位とする。実装順は固定（**M1 を最初に**。ワークスペース境界と認可を後から全体に通すのは手戻りが大きいため）。

| M | テーマ | 主な内容 |
| --- | --- | --- |
| **M0** | 下地 | デモデータ充実、OpenAPI→TS クライアント生成、ADR、新スコープのテスト基盤 |
| **M1** | ワークスペース/チーム土台 | ワークスペース、メンバー/ロール、プロジェクトのワークスペース所属、可視性制御、認可の 3 層化（System/Workspace/Project）、招待＋ユーザー追加 API、System Admin、監査ログ（開始） |
| **M2** | 日常 UX | カスタムワークフロー、カンバン（DnD）、検索/フィルタ/保存ビュー、My Tasks、サブタスク/依存、一括操作、ダークモード、コマンドパレット |
| **M3** | 協働・通知・リアルタイム | @メンション、通知（アプリ内/メール）、ウォッチャー、添付、アクティビティ、WebSocket リアルタイム |
| **M4** | Git 連携 | プロバイダ抽象化、GitHub＋GitLab＋オンプレ GitLab、プライベート対応、Webhook 受信/署名検証/冪等、タスク自動遷移、双方向リンク、identity マッピング |
| **M5** | 見える化・運用・エンタープライズ | 開発指標ダッシュボード、運用形態 2 系統（Terraform / Docker Compose・Helm）、管理コンソール、SSO(SAML)、MFA、インポート/エクスポート、可観測性 |

**到達目標**：M1〜M4 までで、開発チームが実用的に使える一通りが揃う。M5 は余力に応じて着手する。

---

## 11. スコープ外

- **多組織分離（会社間マルチテナント）**：1 インスタンス = 1 組織とするため対象外
- モバイルネイティブアプリ
- Bitbucket 等、GitHub/GitLab 以外の Git ホスティング（抽象化で将来対応可能にはする）

## 12. 用語

| 用語 | 意味 |
| --- | --- |
| 組織 | 本システムを運用する 1 つの会社・チーム（= 1 インスタンス） |
| ワークスペース | 組織内のチーム/部署の単位。可視性・権限の境界 |
| System Admin | インスタンス全体を運用する管理者 |
| Admin / Member / Viewer | ワークスペース内のロール |
| プロバイダ（Git Provider） | GitHub / GitLab / self-managed GitLab |
| identity マッピング | Git アカウントとアプリ内メンバーの対応付け |
| 自己ホスト | 利用者が自身のインフラ（AWS / オンプレ）にアプリを設置して運用する形態 |
