## 1. 背景と目的

Phase 1 で「要件→設計→実装→照合→テスト→セキュリティ見直し→AWS 構築→本番デプロイ」の一連を完了し、`https://tms.accent24.jp` で公開した。機能自体は素朴なプロジェクト/タスク管理であり、プロジェクト/タスク管理 SaaS は Jira・Linear・Backlog 等の激戦区である。

Phase 2 では、機能数で汎用ツールに勝つのではなく、**「開発チーム向け × 自社インフラに置ける × Git と一体 × 効果が指標で見える」**という明確なコンセプトに尖らせ、既存製品に対する選定理由を作る。

### Phase 2 のゴール

- 複数の組織（企業）が利用できる**マルチテナント SaaS / セルフホスト製品**にする
- 開発チームが**日常的に使える**最低限の UX を備える
- **Git（GitHub / GitLab / オンプレ GitLab）と連携**し、チケットを手で動かさなくてよくする
- **自社インフラ（オンプレ・自社クラウド）に閉じて運用できる**配布形態を用意する

---

## 2. プロダクトのコンセプトと差別化

> **「開発チーム向けの、自社に置けるタスク管理。チケットは手で動かさない。」**

| 差別化軸 | 内容 | 既存との違い |
| --- | --- | --- |
| **Git ネイティブ** | ブランチ/PR/MR/パイプラインの状態でタスクが自動遷移。双方向リンク。 | Jira は手動が多い。Linear は連携あるが SaaS 内に閉じる。 |
| **セルフホスト** | 自社クラウド（AWS）/ オンプレに**自分でデプロイ**でき、データは自社保有。 | Linear/Jira Cloud は SaaS 固定でデータは相手クラウド。 |
| **エンジニアリング指標** | Git × タスクのデータから DORA 等を算出し、開発の効果を可視化。 | 一般的な PM ツールは開発指標まで踏み込まない。 |
| **オンプレ GitLab 対応** | gitlab.com だけでなく self-managed GitLab に最初から対応。 | 多くの SaaS は SaaS 版 Git ホスティングのみ。 |

## 3. 想定ユーザー（ペルソナ）

| ペルソナ | 役割 | 主なニーズ |
| --- | --- | --- |
| **開発メンバー** | コードを書く人 | 手でステータス更新したくない。Git 操作がそのまま反映されてほしい。速い UX。 |
| **チームリード / EM** | 開発チームの管理 | 進捗・負荷・ボトルネックを把握したい。DORA 等の指標が欲しい。 |
| **組織管理者** | 組織の設定・メンバー管理 | メンバーの招待・権限管理、組織設定、監査。 |
| **システム運用者** | インスタンスの運用（セルフホスト） | 全組織の管理、SSO・バックアップ・監査、アップグレード。 |

想定の中心は **GitHub / GitLab（オンプレ含む）を使う開発チーム**。セキュリティ要件が厳しく「自社に閉じて使いたい」組織を主なターゲットとする。

## 4. ロール設計（3スコープ）

ロールは**スコープ（管理範囲）ごとに分離**する。システム管理はテナント（組織）を横断する別次元のため、組織内ロールと同一視しない。

| スコープ | ロール | 権限の概要 |
| --- | --- | --- |
| **システム全体**（テナント横断） | **System Admin** | インスタンス運用：全組織・全ユーザーの管理、SSO/システム設定、監査ログ閲覧、バックアップ。セルフホストの運用者がこれにあたる。 |
| **組織内**（テナント内） | **Org Admin** | 組織設定、メンバー招待/削除、ロール付与、（課金） |
| | **Member** | プロジェクト/タスクの作成・編集 |
| | **Viewer** | 閲覧のみ |
| **プロジェクト内** | **OWNER / MEMBER** | 既存のプロジェクト単位の権限（Phase 1 の `ProjectAccess` を拡張。組織ロールの下にぶら下げる） |

### System Admin のアクセス方針

セルフホスト（自社インフラにデータを置く）前提のため、**System Admin はテナントの内容を含むフルアクセスを持つ**。ただし、

- **全操作を監査ログに記録**する（誰が・いつ・何に対して・何をしたか）
- 既定ではテナント内容の閲覧も可能だが、**監査前提**とする
- SaaS 提供に転じる場合は「メタデータ管理のみ＋監査付き一時アクセス（インパーソネート）」に切り替えられる設計にしておく

## 5. マルチテナント方針

- **方式：共有 DB ＋ `organization_id`**（全業務テーブルにテナント識別子を付与）
- EF Core の**グローバルクエリフィルタ**で、現在の組織に属するデータのみを既定で返し、「絞り忘れ」による情報漏えいを防ぐ
- 認可は**テナント対応**に拡張：システム（横断）／組織（テナント内）／プロジェクト（既存）の3層で判定
- データ分離の検証を**自動テストで担保**（別テナントのデータに一切アクセスできないこと）
- 将来の大口テナント向けに、スキーマ/DB 分離へ拡張できる余地を設計に残す（Phase 2 では採用しない）

> 決定の詳細は `docs/phase2/adr/0001-multitenancy.md`（別途作成）に記録する。

**既存データの移行**：Phase 1 の既存データは「デフォルト組織」に所属させる形で移行する（移行方針は M1 の基本設計で定義）。

## 6. Git 連携方針

- **プロバイダ抽象化（`IGitProvider`）**：GitHub / GitLab の差異（Webhook 署名方式・API・認証）をアダプタで吸収する
- **対応プロバイダ**：GitHub、GitLab（gitlab.com）、**self-managed GitLab（オンプレ）**。接続先はベース URL を設定可能にする
- **タスク自動遷移**：ブランチ作成→進行中、PR/MR 作成→レビュー中、マージ→完了。**遷移ルールは組織/プロジェクト単位で設定可能**にする
- **双方向リンク**：タスクからブランチ/PR 作成、`Closes #123` 等でタスク自動クローズ、タスクのタイムラインにコミット/PR/パイプライン結果を表示
- **identity マッピング**：Git ユーザー（GitHub/GitLab）とアプリのメンバーを対応付け、活動を正しく帰属させる
- **Webhook**：署名検証・冪等処理・イベント駆動で受け取る（再送・順序入れ替わりに耐える設計）

## 7. 配布形態

オンプレ GitLab を使う組織は「アプリ自体も自社内に置きたい」ことが多いため、**2系統の配布**を用意する。

| 配布形態 | 用途 | 内容 |
| --- | --- | --- |
| **AWS（Terraform）** | 自社 AWS に構築 | Phase 1 の Terraform をモジュール化し、`terraform apply` で構築 |
| **セルフホスト（Docker Compose / Helm）** | オンプレ・任意環境 | アプリ＋DB を同梱したコンテナ構成で、AWS 非依存に起動できる |

いずれも、設定は環境変数、秘密情報は外部シークレット、ヘルスチェック・マイグレーション手順・バックアップ/リストア手順・アップグレード手順を整備する。

## 8. スコープ（マイルストーン）

各マイルストーンは**単体で完成・デモ可能**な単位とする。実装順は固定（**M1 を最初に**。マルチテナントの後付けは全テーブル・全認可の作り直しになるため）。

| M | テーマ | 主な機能 |
| --- | --- | --- |
| **M0** | 下地 | デモデータ充実、OpenAPI→TS クライアント生成、ADR、新スコープのテスト基盤 |
| **M1** | マルチテナント土台 | 組織（`organizations` / メンバー / 組織ロール）、全テーブルへ `organization_id`、グローバルクエリフィルタ、テナント対応の認可、**招待＋ユーザー追加 API**、System Admin、監査ログ（開始） |
| **M2** | 日常 UX | カスタムワークフロー（状態定義）、カンバン（DnD）、検索/フィルタ/保存ビュー、My Tasks、サブタスク/依存、一括操作、ダークモード、コマンドパレット |
| **M3** | 協働・通知・リアルタイム | @メンション、通知（アプリ内 / メール(SES) / Slack）、ウォッチャー、添付(S3)、アクティビティ、WebSocket リアルタイム、サイクル/スプリント |
| **M4** | Git 連携（差別化の核） | プロバイダ抽象化、GitHub＋GitLab＋オンプレ GitLab、Webhook 受信/署名検証/冪等、タスク自動遷移、双方向リンク、identity マッピング |
| **M5** | 指標・配布・エンタープライズ | DORA/エンジニアリング指標ダッシュボード、配布2系統（Terraform / Docker Compose・Helm）、管理コンソール、SSO(SAML)、MFA、インポート/エクスポート、可観測性 |

**到達目標**：ポートフォリオとしては **M1〜M4** までで一貫したストーリーが完成する。M5 は余力に応じて「配布2系統」「指標」を優先して着手する。

## 9. 非機能要件

| 分類 | 要件 |
| --- | --- |
| **セキュリティ** | テナント間の完全なデータ分離、認可の集約と自動テストでの担保、監査ログ、MFA、SSO(SAML/将来 SCIM)、既存のセキュリティ対策（BFF・CSP nonce・レート制限・最小権限 等）を維持 |
| **可観測性** | 構造化ログ、主要メトリクス、分散トレース、アラート。運用者が状態を把握できること |
| **性能/拡張** | Lambda + RDS の接続枯渇対策（RDS Proxy 等の検討）、ページネーション、クエリの N+1 回避 |
| **テスト** | 既存の UT/API/結合/画面/システム/セキュリティ方針を踏襲。テナント分離・認可は重点的にテスト |
| **国際化** | 日本語/英語（最低限、文言の外部化） |
| **アクセシビリティ** | キーボード操作、コントラスト、スクリーンリーダー配慮 |
| **運用** | マイグレーション手順、バックアップ/リストア、アップグレード、設定の文書化 |

---

## 10. スコープ外

- 課金・サブスクリプション課金基盤（入口となる組織/プラン概念は持つが、決済連携は Phase 2 では対象外）
- モバイルネイティブアプリ
- Bitbucket 等 GitHub/GitLab 以外の Git ホスティング（抽象化で将来対応可能にはする）
- AI による自動要約・自動起票（将来候補）

## 11. 用語

| 用語 | 意味 |
| --- | --- |
| テナント / 組織（Organization） | 利用企業・チームの単位。データ分離の境界。 |
| System Admin | インスタンス全体を運用する管理者（テナント横断） |
| Org Admin / Member / Viewer | 組織内のロール |
| プロバイダ（Git Provider） | GitHub / GitLab / self-managed GitLab |
| DORA | 開発パフォーマンス指標（デプロイ頻度・変更リードタイム・変更失敗率・MTTR） |
| セルフホスト | 利用者が自身のインフラ（AWS / オンプレ）にアプリを設置して運用する形態 |
