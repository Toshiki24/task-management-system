# 2. 見直しの経緯

MVPの画面・API実装および設計書との照合（#8）が完了した時点で、AWSデプロイ前にセキュリティ面の見直しを実施した。

見直しの観点は以下とする。

* XSS（クロスサイトスクリプティング）
* CSRF（クロスサイトリクエストフォージェリ）
* 認証トークンの保管方法と有効期限（リフレッシュトークン）
* 認可（アクセス制御）
* その他、デプロイ先（AWS）の構成に起因する懸念

見直しの結果、実装済みのコードに設計書（基本設計書 17章「認可チェック」）と乖離する重大な問題が見つかったため、対応方針と優先順位を本書で定め、順次対応する。

# 3. 見直し時点の構成

```text
ブラウザ
   │  Authorization: Bearer {JWT}
   │  （JWTは localStorage に保存）
   ▼
ASP.NET Core Web API ── PostgreSQL
```

| 項目        | 見直し時点の状態                                     |
| --------- | -------------------------------------------- |
| 認証方式      | JWT（HS256）。ログインAPIで発行                        |
| トークン保存先   | ブラウザの `localStorage`                           |
| トークン有効期限  | 60分。リフレッシュトークンなし                              |
| API呼び出し   | ブラウザから API を直接呼び出す（CORS で `localhost:3000` を許可） |
| 認可        | 「ログイン済みか」のみ判定。プロジェクトへの所属・権限は判定していない          |
| フロントエンド   | Next.js 16.3.5。画面はクライアントコンポーネントで描画              |
| デプロイ予定    | Amplify（Next.js）＋ API Gateway / Lambda（API）    |

# 4. 現状評価

## 4.1 対策済みの事項

| 項目               | 内容                                                 |
| ---------------- | -------------------------------------------------- |
| パスワードの保存         | BCrypt でハッシュ化して保存している                              |
| SQLインジェクション      | EF Core / LINQ を使用し、生SQLを組み立てていない                   |
| XSS（出力時）         | React の自動エスケープのみで描画し、`dangerouslySetInnerHTML` を使用していない |
| CSRF             | Cookie を使わず Authorization ヘッダーで認証しているため、CSRF は成立しない   |
| 内部情報の非公開         | 未処理例外・入力形式エラー時に、スタックトレースや内部例外メッセージを返さない            |
| 認証必須の既定化         | `FallbackPolicy` により、ログインAPI以外は認証必須                  |
| CORS             | 許可オリジンを設定ファイルで明示している（ワイルドカード不使用）                   |
| 秘密情報             | 本番用の署名鍵・接続文字列をリポジトリに含めない方針                         |

# 5. 課題ごとの対策

## 5.1 SEC-01 認可チェック

プロジェクトへの所属とプロジェクト内権限（OWNER / MEMBER）に基づいて、API ごとに操作可否を判定する。

MVP における権限は以下とする。

| 操作                   | OWNER | MEMBER | 非メンバー |
| -------------------- | :---: | :----: | :---: |
| プロジェクト一覧            | 所属分のみ | 所属分のみ  | －     |
| プロジェクト作成            | ○（作成者がOWNERになる） | ○      | ○     |
| プロジェクト参照            | ○     | ○      | ×     |
| プロジェクト編集・削除         | ○     | ×      | ×     |
| メンバー一覧              | ○     | ○      | ×     |
| メンバー追加・削除           | ○     | ×      | ×     |
| タスク一覧・参照・作成・編集      | ○     | ○      | ×     |
| タスク削除               | ○     | ×      | ×     |
| コメント一覧・登録           | ○     | ○      | ×     |

* 非メンバーがプロジェクト配下のリソースにアクセスした場合は `404` を返し、リソースの存在自体を開示しない。
* メンバーだが権限が不足している場合は `403` を返す。
* 判定はコントローラーではなくサービス層（またはリソースベース認可）で共通化し、判定漏れを防ぐ。

**要件定義書との差異**

要件定義書 10章では「管理者」「プロジェクト管理者」「メンバー」のシステムロールで操作可否を定めているが、現行のDBにはシステムロールを保持する列がない。MVPではプロジェクト内権限（OWNER / MEMBER）で代替し、以下は暫定とする。

* プロジェクト作成は認証済みの全ユーザーに許可する（作成者がOWNERになる）。
* 要件で「△（本人作成分のみ）」とされたタスク削除は、タスクに作成者列がないため OWNER のみに許可する。
* システム管理者ロールは MVP 以降の拡張とする。

## 5.2 SEC-02 / SEC-03 ログイン保護

* ログインAPIに試行回数の上限を設ける（例：同一IPから1分間に5回まで）。超過時は `429 Too Many Requests` を返す。
* 本番環境の API は Lambda 上で動作し、インスタンスごとにメモリが分かれるため、アプリ内のレート制限だけでは十分に機能しない。本番では **API Gateway のスロットリング**または **AWS WAF のレートベースルール**で制限し、アプリ内のレート制限はローカル環境および多層防御として位置付ける。
* 存在しないメールアドレスの場合もダミーのハッシュで BCrypt 検証を行い、応答時間を揃える。

## 5.3 SEC-04 / SEC-05 トークン管理（BFF構成への移行）

Next.js のサーバー機能（Route Handler）を BFF（Backend for Frontend）として利用し、**トークンをブラウザの JavaScript から扱えない場所に移す**。

```text
ブラウザ
   │  HttpOnly セッションCookie（JSから読み取り不可）
   ▼
Next.js（Amplify Hosting SSR）… BFF
   │  Authorization: Bearer {アクセストークン}
   ▼
API Gateway / Lambda（ASP.NET Core Web API）
   │
   ▼
RDS for PostgreSQL
```

| 項目           | 方針                                                               |
| ------------ | ---------------------------------------------------------------- |
| アクセストークン     | JWT。有効期限を15分程度に短縮する。BFF のみが保持し、ブラウザには渡さない                         |
| リフレッシュトークン   | 推測不可能なランダム値。有効期限は7〜14日。DB にはハッシュ値のみを保存する                          |
| ローテーション      | リフレッシュのたびに新しいトークンへ置き換え、古いトークンは失効させる                                |
| 再利用検知        | 失効済みのリフレッシュトークンが使われた場合は漏洩とみなし、該当ユーザーの全トークンを失効させる                  |
| ログアウト        | リフレッシュトークンを DB 上で失効させ、セッションCookie を削除する                            |
| セッションCookie  | `HttpOnly`、`Secure`、`SameSite=Lax` 以上、`Path=/`                   |
| セッションの保存先    | Amplify の SSR はサーバーレスでメモリを保持できないため、暗号化Cookie またはDB等の外部ストアに保存する（実装時に決定） |
| API の直接呼び出し  | ブラウザから API Gateway を直接呼び出さない。API 側の CORS 許可は不要になる                  |

## 5.4 CSRF 対策（BFF 移行に伴う追加対策）

BFF 移行後はセッションCookie による認証となり、BFF 上の**すべての更新系リクエスト**が CSRF の対象になるため、以下を組み合わせて対策する。

* セッションCookie に `SameSite=Lax` 以上を設定する。
* 更新系リクエスト（POST / PUT / DELETE）で `Origin` ヘッダーを検証し、自サイト以外からのリクエストを拒否する。
* 更新系リクエストに独自ヘッダー（例：`X-Requested-With`）の付与を必須とする。

## 5.5 SEC-06 XSS 対策・セキュリティヘッダー

BFF 移行によりトークンは盗まれなくなるが、XSS が発生すると、画面を開いている間は攻撃者のスクリプトが本人として BFF を呼び出せる。このため、XSS そのものの対策も継続する。

* `Content-Security-Policy` を設定する（`script-src 'self'`、`object-src 'none'`、`frame-ancestors 'none'` 等）。
* `X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`X-Frame-Options: DENY` を設定する。
* `dangerouslySetInnerHTML` の使用を ESLint（`react/no-danger`）で禁止する。将来 Markdown 等を表示する場合は DOMPurify 等で無害化する。
* ユーザー入力値を `href` 等の URL 属性に使用する場合は、`http:` / `https:` 以外のスキームを拒否する。

## 5.6 その他（SEC-07 〜 SEC-11）

| ID     | 対策                                                                  |
| ------ | ------------------------------------------------------------------- |
| SEC-07 | `ClockSkew` を30秒程度に短縮する。起動時に署名鍵の長さ（32バイト以上）を検証する                        |
| SEC-08 | 本番環境でのみ `UseHsts()` を有効にする                                         |
| SEC-09 | ユーザー一覧APIの返却範囲・項目を見直す（メンバー追加画面の仕様と合わせて決定する）                          |
| SEC-10 | タスクの担当者はプロジェクトメンバーに限定する                                             |
| SEC-11 | `npm audit` / `dotnet list package --vulnerable` を CI に組み込む、または Dependabot を有効にする |

# 6. 設計判断

## 6.1 BFF 構成の採用

**判断**：Next.js の Route Handler を BFF として利用し、トークンは BFF のみが保持する。

**理由**

* デプロイ先の既定ドメインは、フロントエンドが `*.amplifyapp.com`、API が `*.execute-api.*.amazonaws.com` となり、**別サイト（cross-site）扱い**になる。
* このため、API が発行する Cookie でリフレッシュトークンを扱う方式では、`SameSite=None` が必須となる。さらに Safari・Firefox 等のサードパーティCookieブロックにより、Cookie が送信されない可能性が高い。
* BFF 構成であれば、ブラウザが通信する相手は Next.js のみとなり、Cookie を常にファーストパーティとして扱える。
* トークンがブラウザの JavaScript から読み取れなくなり、SEC-04 を根本的に解消できる。

**トレードオフ**

* Next.js をサーバー（Amplify Hosting の SSR）として動作させる必要があり、静的ホスティングは使用できない。
* CSRF の対象が BFF のすべての更新系リクエストに広がるため、5.4 の対策が必須となる。
* 経由する処理が1段増えるため、レイテンシと障害点が増える。

## 6.2 Next.js 15 への固定

**判断**：Next.js を 16.3.5 から 15 系の最新パッチへ変更し、バージョンを固定する。

**理由**

* BFF には Next.js のサーバー機能が必要なため、Amplify Hosting の SSR（Amplify Hosting compute）を利用する。
* 2026-09-28 時点の AWS 公式ドキュメントでは、Amplify Hosting compute の対応範囲は **Next.js 12〜15** であり、16 は公式サポート外である。
* Next.js 16.1 以降では、Turbopack が生成するシンボリックリンクを Amplify のデプロイ処理が扱えずに失敗する既知の不具合（aws-amplify/amplify-hosting#4074、未解決）がある。
* 現状の依存構成では当該不具合に該当しない可能性もあるが、公式サポート外の構成に依存しない方が保守性（基本設計書 19.3）の観点で望ましいと判断した。
* 現行コードは Next.js 15 でも利用可能な API のみを使用しており、変更範囲は設定ファイルが中心となる。

Amplify が Next.js 16 に公式対応した時点で、バージョンアップを再検討する。

**利用上の制約（Amplify Hosting compute）**

* Edge Runtime（Edge Middleware / Edge API Routes）は非対応のため、BFF は Node.js ランタイムで実装する。
* ストリーミング、`after()` は非対応。
* SSR のデプロイサイズは 50MB まで。

## 6.3 検討したが採用しなかった案

| 案                                    | 不採用の理由                                                        |
| ------------------------------------ | ------------------------------------------------------------- |
| 現状維持（localStorage に JWT を保存）          | XSS 発生時にトークンが盗まれる。失効手段もない                                     |
| アクセストークンはメモリ、リフレッシュトークンは API の HttpOnly Cookie | 独自ドメインを用意しない限り cross-site となり、サードパーティCookieブロックにより動作しない可能性が高い       |
| Next.js 16 のまま Amplify にデプロイ           | 公式サポート外であり、既知の不具合が未解決                                          |
| フロントエンドを OpenNext（Lambda + CloudFront）や ECS に変更 | Next.js 16 を継続できるが、基本設計書の AWS 構成の変更とインフラ構築の作業量が増える                |
