# 2. 見直しの経緯

MVPの画面・API実装および設計書との照合（#8）が完了した時点で、AWSデプロイ前にセキュリティ面の見直しを実施した。

見直しの観点は以下とする。

* XSS（クロスサイトスクリプティング）
* CSRF（クロスサイトリクエストフォージェリ）
* 認証トークンの保管方法と有効期限（リフレッシュトークン）
* 認可（アクセス制御）
* その他、デプロイ先（AWS）の構成に起因する懸念

見直しの結果、実装済みのコードに設計書（基本設計書 17章「認可チェック」）と乖離する重大な問題が見つかったため、対応方針と優先順位を本書で定め、順次対応する。

# 3. 見直し時点の構成

```text
ブラウザ
   │  Authorization: Bearer {JWT}
   │  （JWTは localStorage に保存）
   ▼
ASP.NET Core Web API ── PostgreSQL
```

| 項目        | 見直し時点の状態                                     |
| --------- | -------------------------------------------- |
| 認証方式      | JWT（HS256）。ログインAPIで発行                        |
| トークン保存先   | ブラウザの `localStorage`                           |
| トークン有効期限  | 60分。リフレッシュトークンなし                              |

| デプロイ予定    | Amplify（Next.js）＋ API Gateway / Lambda（API）    |

# 5. 課題ごとの対策

## 5.1 SEC-01 認可チェック

プロジェクトへの所属とプロジェクト内権限（OWNER / MEMBER）に基づいて、API ごとに操作可否を判定する。

MVP における権限は以下とする。

| 操作                   | OWNER | MEMBER | 非メンバー |
| -------------------- | :---: | :----: | :---: |
| プロジェクト一覧            | 所属分のみ | 所属分のみ  | －     |
| プロジェクト作成            | ○（作成者がOWNERになる） | ○      | ○     |
| プロジェクト参照            | ○     | ○      | ×     |
| プロジェクト編集・削除         | ○     | ×      | ×     |
| メンバー一覧              | ○     | ○      | ×     |
| メンバー追加・削除           | ○     | ×      | ×     |
| タスク一覧・参照・作成・編集      | ○     | ○      | ×     |
| タスク削除               | ○     | ×      | ×     |
| コメント一覧・登録           | ○     | ○      | ×     |

* 非メンバーがプロジェクト配下のリソースにアクセスした場合は `404` を返し、リソースの存在自体を開示しない。
* メンバーだが権限が不足している場合は `403` を返す。
* 判定はコントローラーではなくサービス層（またはリソースベース認可）で共通化し、判定漏れを防ぐ。

**要件定義書との差異**

要件定義書 10章では「管理者」「プロジェクト管理者」「メンバー」のシステムロールで操作可否を定めているが、現行のDBにはシステムロールを保持する列がない。MVPではプロジェクト内権限（OWNER / MEMBER）で代替し、以下は暫定とする。

* プロジェクト作成は認証済みの全ユーザーに許可する（作成者がOWNERになる）。
* 要件で「△（本人作成分のみ）」とされたタスク削除は、タスクに作成者列がないため OWNER のみに許可する。
* システム管理者ロールは MVP 以降の拡張とする。

## 5.2 SEC-02 / SEC-03 ログイン保護

* ログインAPIに試行回数の上限を設ける。**同一メールアドレスで、最初の失敗から60秒以内に5回失敗したら、その60秒が経過するまでログインを受け付けない**。超過時は `429 Too Many Requests` と `Retry-After` ヘッダーを返す。
  * 制限中は、パスワードが正しくても照合せずに429を返す（総当たりを続けても正解が分からないようにする）。
  * 登録されていないメールアドレスも同じように数える。登録済みのアドレスだけが制限されると、429の有無から登録状況を推測できてしまうため。
  * メールアドレスは大文字・小文字と前後の空白を正規化して数え、表記を変えるだけで制限を回避できないようにする。
  * ログインに成功すると失敗回数をリセットする。
* **制限の単位はIPアドレスではなくメールアドレス（アカウント）とする。**
  * BFF構成（5.3）では、APIから見た送信元IPがすべて BFF になる。アプリ内でIP単位に制限すると、全ユーザーのログインがまとめて制限されてしまう。
  * メールアドレス単位の制限は、同じアカウントへの総当たりには有効だが、多数のアカウントに同じパスワードを試す攻撃（パスワードスプレー）には効かない。これは **API Gateway のスロットリング**または **AWS WAF のレートベースルール**（IP単位）で防ぐ。
  * 第三者が他人のメールアドレスでわざと失敗を繰り返すと、本人も一時的にログインできなくなる。影響を60秒に限定することで許容する。
* 失敗回数はアプリのメモリ上に保持するため、再起動で消え、Lambda の複数インスタンス間では共有されない。本番では上記の API Gateway / AWS WAF による制限と組み合わせ、アプリ内の制限は多層防御として位置付ける。
* 存在しないメールアドレスの場合もダミーのハッシュで BCrypt 照合を行い、応答時間を揃える。ダミーのハッシュは、実際のユーザーと同じコスト（BCrypt.Net の既定値11）で生成する。
  * 修正前は、存在しないメールアドレスの応答（中央値 5.2ms）がパスワード誤り（中央値 174.9ms）より約34倍速く、応答時間から登録状況を推測できることをテスト（SEC-03-01）で確認した。

## 5.3 SEC-04 / SEC-05 トークン管理（BFF構成への移行）

Next.js のサーバー機能（Route Handler）を BFF（Backend for Frontend）として利用し、**トークンをブラウザの JavaScript から扱えない場所に移す**。

```text
ブラウザ
   │  HttpOnly セッションCookie（JSから読み取り不可）
   ▼
Next.js（Amplify Hosting SSR）… BFF
   │  Authorization: Bearer {アクセストークン}
   ▼
API Gateway / Lambda（ASP.NET Core Web API）
   │
   ▼
RDS for PostgreSQL
```

| 項目           | 方針                                                               |
| ------------ | ---------------------------------------------------------------- |
| アクセストークン     | JWT。有効期限は15分。BFF のみが保持し、ブラウザには渡さない                         |
| リフレッシュトークン   | 推測不可能なランダム値（32バイト）。有効期限は7日。DB（`refresh_tokens`）には SHA-256 のハッシュ値のみを保存する                          |
| ローテーション      | リフレッシュのたびに新しいトークンへ置き換え、古いトークンは失効させる                                |
| 再利用検知        | 置き換え済みのリフレッシュトークンが使われた場合は漏洩とみなし、該当ユーザーの全トークンを失効させる。ただし置き換えから10秒以内は、同時リクエストによる正常な利用として許容する（6.4 参照） |
| ログアウト        | リフレッシュトークンを DB 上で失効させ、セッションCookie を削除する                            |
| セッションCookie  | `HttpOnly`、`Secure`、`SameSite=Lax` 以上、`Path=/`                   |
| セッションの保存先    | **暗号化Cookie** に保存する（6.4 参照）。BFF はトークンを暗号化して HttpOnly Cookie に入れ、サーバー側にセッション用のストアを持たない |
| API の直接呼び出し  | ブラウザから API Gateway を直接呼び出さない。API 側の CORS 設定は削除し、他のオリジンのブラウザからの呼び出しを許可しない |

## 5.4 CSRF 対策（BFF 移行に伴う追加対策）

BFF 移行後はセッションCookie による認証となり、BFF 上の**すべての更新系リクエスト**が CSRF の対象になるため、以下を組み合わせて対策する。

* セッションCookie に `SameSite=Lax` を設定する。
* 更新系リクエスト（POST / PUT / DELETE / PATCH）で `Origin` ヘッダーを検証し、ホストが自サイト（`Host`、プロキシ経由の場合は `X-Forwarded-Host`）と一致しないリクエストを拒否する。`Origin` ヘッダーがないリクエストも拒否する。
* 更新系リクエストに独自ヘッダー `X-Requested-With: XMLHttpRequest` の付与を必須とする。独自ヘッダーを付けたクロスオリジンのリクエストにはプリフライトが必要になり、BFF は CORS を許可していないため、他サイトからは送信できない。
* ログインもCSRFの対象とする（攻撃者のアカウントでログインさせる「ログインCSRF」を防ぐ）。
* 参照系（GET）は状態を変更しないため、上記の確認の対象外とする。

## 5.5 SEC-06 XSS 対策・セキュリティヘッダー

BFF 移行によりトークンは盗まれなくなるが、XSS が発生すると、画面を開いている間は攻撃者のスクリプトが本人として BFF を呼び出せる。このため、XSS そのものの対策も継続する。

**画面（Next.js、`frontend/next.config.ts`）**

* `Content-Security-Policy` を設定する。

  | ディレクティブ         | 値                                   | 目的                                       |
  | --------------- | ----------------------------------- | ---------------------------------------- |
  | default-src     | `'self'`                            | 読み込み元を自サイトに限定する                          |
  | script-src      | `'self' 'unsafe-inline'`（開発時のみ `'unsafe-eval'` も追加） | 外部サイトのスクリプトの読み込みを禁止する（下記の制約を参照）          |
  | style-src       | `'self' 'unsafe-inline'`            | スタイルの読み込み元を自サイトに限定する                     |
  | img-src         | `'self' data: blob:`                | 画像の読み込み元を限定する                            |
  | font-src        | `'self'`                            | フォントは `next/font` により自サイトから配信する            |
  | connect-src     | `'self'`（開発時のみ `ws:` も追加）         | 通信先をBFF（同一オリジン）に限定し、XSSで盗んだ情報を外部へ送信されるのを防ぐ |
  | object-src      | `'none'`                            | プラグイン（`<object>` 等）を禁止する                   |
  | base-uri        | `'self'`                            | `<base>` タグによる相対URLの書き換えを防ぐ               |
  | form-action     | `'self'`                            | フォームの送信先を自サイトに限定する                       |
  | frame-ancestors | `'none'`                            | 他サイトの iframe に埋め込ませない（クリックジャッキング対策）        |

* `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Referrer-Policy: strict-origin-when-cross-origin`、`Permissions-Policy`（カメラ・マイク・位置情報を無効化）を設定する。
* `X-Powered-By: Next.js` ヘッダーを出力しない（使用しているフレームワークを外部に知らせない）。

**`script-src` に `'unsafe-inline'` を許可した理由と制約**

* 当初は `script-src 'self'` とする方針だったが、実際に設定したところ、Next.js（App Router）がページの描画に使うインラインスクリプト（ログイン画面で7つ）がすべてブロックされ、画面が動作しなかった。
* インラインスクリプトの内容はページ・リクエストごとに変わるため、ハッシュ値での許可はできない。
* リクエストごとに発行する nonce で許可する方式は最も安全だが、middleware が必要で、全ページがリクエストごとの描画になる。デプロイ先の Amplify Hosting は Edge ランタイムの middleware に対応しておらず、Node.js ランタイムの middleware への対応も未確認のため、見送った。
* `'unsafe-inline'` を許可しているため、HTMLに注入されたインラインスクリプトはCSPでは防げない。XSSの防止は、React の自動エスケープ、`dangerouslySetInnerHTML` の禁止（下記）に依存する。一方、外部サイトのスクリプトの読み込みと、外部への通信（`connect-src 'self'`）はCSPで防げる。
* **残課題**：デプロイ時に Amplify での middleware の対応状況を確認し、対応していれば nonce 方式への切り替えを検討する。

**API（ASP.NET Core、`Program.cs`）**

* すべてのレスポンス（エラーを含む）に `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Content-Security-Policy: default-src 'none'; frame-ancestors 'none'` を付与する。JSONのみを返すAPIのため、あらゆるリソースの読み込みを禁止する（開発時の Swagger UI は対象外）。
* `Server: Kestrel` ヘッダーを出力しない。

**コーディング規約（ESLint）**

* `dangerouslySetInnerHTML` の使用を `react/no-danger` で禁止する。将来 Markdown 等を表示する場合は DOMPurify 等で無害化する。
* `href` 等への `javascript:` URL の記述を `react/jsx-no-script-url` で禁止する。
* ユーザー入力値を `href` 等の URL 属性に使用する場合は、`http:` / `https:` 以外のスキームを拒否する（現時点で該当箇所はない）。

## 5.6 その他（SEC-07 〜 SEC-13）

| ID     | 対策                                                                  |
| ------ | ------------------------------------------------------------------- |
| SEC-07 | `ClockSkew` を30秒に短縮する。署名鍵（`Jwt:Key`）が未設定または32バイト未満の場合は起動時にエラーにする（`JwtSigningKey` に集約し、発行と検証で同じ処理を使う） |
| SEC-08 | 本番環境でのみ HSTS を有効にする（API：`UseHsts()`、画面：`Strict-Transport-Security: max-age=31536000; includeSubDomains`）。API の HSTS は、ASP.NET Core が localhost を対象外とし、E2Eテストは Development 環境で動作するため、ローカルでは確認できない。デプロイ後に確認する |
| SEC-09 | **リスク受容**とする（下記参照）                                                      |
| SEC-10 | タスクの担当者はプロジェクトメンバーに限定する                                             |
| SEC-11 | `npm audit` / `dotnet list package --vulnerable` を CI に組み込む、または Dependabot を有効にする |
| SEC-12 | プロジェクトの最後のOWNERは削除できないようにする（409）                                        |
| SEC-13 | メンバー削除時に、そのプロジェクトでそのユーザーが担当者のタスクを未割り当てにする（メンバー削除と同じトランザクションで保存する） |

**SEC-09 をリスク受容とした理由**

* 本システムは社内（組織内）で利用するタスク管理システムであり、利用者は組織内のメンバーに限られる。組織内の利用者どうしが氏名・メールアドレスを確認できることは、一般的な業務システム（チャットツールの社員一覧等）と同等である。
* 要件定義書 7.2 でも「ユーザー一覧表示」を機能として定義しており、利用者どうしが一覧を参照できることは要件上想定された動作である。
* メンバー追加画面では、同名のユーザーを区別するためにメールアドレスを表示しており、返却項目から外すと操作性が下がる。
* ユーザーの登録は管理者が行う前提とし（セルフサインアップの機能はない）、組織外の人がユーザーとして登録されることはない。

**前提が変わった場合の見直し**：組織外の人（取引先等）をユーザーとして登録する場合や、セルフサインアップを追加する場合は、メンバー追加をメールアドレス入力方式に変更し、ユーザー一覧APIの返却範囲を制限する。

# 6. 設計判断

## 6.1 BFF 構成の採用

**判断**：Next.js の Route Handler を BFF として利用し、トークンは BFF のみが保持する。

**理由**

* デプロイ先の既定ドメインは、フロントエンドが `*.amplifyapp.com`、API が `*.execute-api.*.amazonaws.com` となり、**別サイト（cross-site）扱い**になる。
* このため、API が発行する Cookie でリフレッシュトークンを扱う方式では、`SameSite=None` が必須となる。さらに Safari・Firefox 等のサードパーティCookieブロックにより、Cookie が送信されない可能性が高い。
* BFF 構成であれば、ブラウザが通信する相手は Next.js のみとなり、Cookie を常にファーストパーティとして扱える。
* トークンがブラウザの JavaScript から読み取れなくなり、SEC-04 を根本的に解消できる。

**トレードオフ**

* Next.js をサーバー（Amplify Hosting の SSR）として動作させる必要があり、静的ホスティングは使用できない。
* CSRF の対象が BFF のすべての更新系リクエストに広がるため、5.4 の対策が必須となる。
* 経由する処理が1段増えるため、レイテンシと障害点が増える。

## 6.2 Next.js 15 への固定

**判断**：Next.js を 16.3.5 から 15 系の最新パッチへ変更し、バージョンを固定する。

**理由**

* BFF には Next.js のサーバー機能が必要なため、Amplify Hosting の SSR（Amplify Hosting compute）を利用する。
* 2026-09-28 時点の AWS 公式ドキュメントでは、Amplify Hosting compute の対応範囲は **Next.js 12〜15** であり、16 は公式サポート外である。
* Next.js 16.1 以降では、Turbopack が生成するシンボリックリンクを Amplify のデプロイ処理が扱えずに失敗する既知の不具合（aws-amplify/amplify-hosting#4074、未解決）がある。
* 現状の依存構成では当該不具合に該当しない可能性もあるが、公式サポート外の構成に依存しない方が保守性（基本設計書 19.3）の観点で望ましいと判断した。
* 現行コードは Next.js 15 でも利用可能な API のみを使用しており、変更範囲は設定ファイルが中心となる。

Amplify が Next.js 16 に公式対応した時点で、バージョンアップを再検討する。

**利用上の制約（Amplify Hosting compute）**

* Edge Runtime（Edge Middleware / Edge API Routes）は非対応のため、BFF は Node.js ランタイムで実装する。
* ストリーミング、`after()` は非対応。
* SSR のデプロイサイズは 50MB まで。

**ダウングレードに伴う依存ライブラリの脆弱性**

* Next.js 15 系（最新の 15.5.26 を含む）は、内部で PostCSS 8.4.31 を固定しており、既知の脆弱性（`npm audit` で high）がある。Next.js 16.3.5 では修正版（8.5.23）が使われていたため、ダウングレードによって新たに検出されるようになった。
* 当該の脆弱性は、攻撃者が用意したCSSを PostCSS で処理した場合に問題となるもの（XSS、ソースマップ経由のファイル読み取り）である。本システムでは PostCSS はビルド時に自前のCSSを処理するだけで、ユーザーが入力したCSSは処理しないため、実際に悪用される可能性は低い。
* ただし、脆弱性の警告を残したままにしないため、`frontend/package.json` の `overrides` で Next.js 内部の PostCSS を修正版（8.5.23以上）に置き換えた。置き換え後に `npm audit` が0件になること、ビルドと全項目の回帰テストが成功することを確認している。

## 6.4 BFFのセッション保存先とリフレッシュの同時実行

**判断**：BFF のセッション（アクセストークン、リフレッシュトークン、ユーザー情報）は暗号化Cookie に保存する。リフレッシュトークンの置き換えには10秒の猶予期間を設ける。

**セッションの保存先を暗号化Cookie にした理由**

* Amplify Hosting の SSR はサーバーレスで、リクエスト間でメモリを保持できない。
* DB等にセッションを保存する方式と比べ、セッション用のテーブルやストアが不要で、構成が単純になる。
* リフレッシュトークンの失効は API 側の `refresh_tokens` で管理するため、Cookie 自体をサーバー側から無効化できなくても、ログアウトや再利用検知の後はアクセストークンの有効期限（15分）が過ぎた時点で使えなくなる。

**暗号化Cookie の制約**

* Cookie が盗まれた場合、中のアクセストークンは有効期限（15分）まで使える。アクセストークンを短命にしているのはこのためである。
* 暗号化の鍵は環境変数で管理する。鍵を変更すると全ユーザーがログアウトされる。
* Cookie の上限（約4KB）に収まるよう、保存する情報を必要最小限にする。

**猶予期間を設けた理由**

アクセストークンの有効期限が切れた直後に、画面から複数のAPI呼び出しが同時に送られると、それぞれが同じリフレッシュトークンで置き換えを行う。最初の置き換えで元のトークンは失効するため、猶予期間がないと2つ目以降が「再利用」と判定され、正規の利用者が強制的にログアウトされてしまう。

猶予期間内の再利用ではそれぞれに新しいトークンを発行し、猶予期間を過ぎた再利用だけを漏洩として扱う。猶予期間（10秒）の間は、盗んだトークンでも再発行できてしまうが、攻撃者がその短い間にトークンを入手して使う必要があり、リスクは限定的と判断した。

## 6.3 検討したが採用しなかった案

| 案                                    | 不採用の理由                                                        |
| ------------------------------------ | ------------------------------------------------------------- |
| 現状維持（localStorage に JWT を保存）          | XSS 発生時にトークンが盗まれる。失効手段もない                                     |
| BFFのセッションをDB等のサーバー側ストアに保存                         | セッション用のテーブル・ストアが必要になる。暗号化Cookie でも、リフレッシュトークンの失効はAPI側で管理できるため採用しなかった |
| アクセストークンはメモリ、リフレッシュトークンは API の HttpOnly Cookie | 独自ドメインを用意しない限り cross-site となり、サードパーティCookieブロックにより動作しない可能性が高い       |
| Next.js 16 のまま Amplify にデプロイ           | 公式サポート外であり、既知の不具合が未解決                                          |
| フロントエンドを OpenNext（Lambda + CloudFront）や ECS に変更 | Next.js 16 を継続できるが、基本設計書の AWS 構成の変更とインフラ構築の作業量が増える                |
