# 2. 本書の位置づけと経緯

第1回のセキュリティ見直し（`security-review.md`、2026-09-28〜29）は、MVP実装と設計書の照合（アプリ層の XSS / CSRF / 認可 / トークン管理等）を対象とし、SEC-01〜SEC-13 を対応済みとした。その後 AWS 構成設計書（`aws-architecture.md`）を作成し、受容するリスク（同§5.4）を明示した。

本書（第2回）は、**AWSへのデプロイ作業の途中（ネームサーバー変更の反映待ち）** に、改めて **攻撃者視点の脅威モデリング** を行い、第1回レビューおよび AWS構成設計書の「受容するリスク」に**記載されていなかった盲点**を洗い出して記録するものである。

* 第1回レビューの記録（SEC-01〜SEC-13）は**書き換えない**（ある時点の記録として保全する）。本書は独立した第2回の記録とする。
* 本書の課題 ID は、第1回（SEC-xx）と区別するため **SEC2-xx** とする。
* コスト方針は要件定義書 13.3・19章および `aws-architecture.md` 2.2 を踏襲し、**費用を最優先**とする。原則として追加の常時課金サービス（WAF・GuardDuty・マルチAZ 等）は導入せず、コード・Terraform 設定・運用で対応できるものを採る。

**見直しの観点（第2回）**

* 公開される API Gateway エンドポイントの直接攻撃（DoS・総当たり）
* BFF〜API 間の共有秘密（`X-Origin-Verify`）の強度・運用
* 単一コンポーネント侵害時の波及（JWT 署名鍵、CI/CD の権限）
* バックアップ・監査・DNS など、敵対者を想定した運用面
* 第1回・AWS構成設計書で「受容」と明記していないリスクの有無

# 4. 新規に検出した盲点（SEC2-01〜SEC2-11）

第1回レビュー・AWS構成設計書 §5.4 に記載がなかったものを対象とする。「受容済み」との線引きは6章に示す。

| ID | 盲点 | 重大度 | 内容 |
| --- | --- | :-: | --- |
| SEC2-01 | 公開 API への認証不要の L7 DoS | 高 | `X-Origin-Verify` の検証は API（Lambda）側で行うため、誤ったヘッダーでもリクエストは Lambda に到達してから 403 になる。正規トラフィックは全て BFF 経由で**ステージ全体の同一スロットリング枠（20rps）・予約同時実行（10）を共有**するため、公開 API URL へゴミリクエストを送るだけで、秘密も認証もなく全利用者を 429 に追い込める |
| SEC2-02 | `X-Origin-Verify` が単一・静的・強度未保証 | 高 | API 境界の防御がこの共有秘密1本に集約されているが、`Jwt:Key`・`SESSION_SECRET` と異なり**最小強度チェックがなく、ローテーション手順・漏洩時対応も未定義**。漏洩すると BFF をなりすまして API を直接呼び、CSRF 対策・セッション管理を恒久的にバイパスできる |
| SEC2-03 | 低速パスワードスプレーが検知・制限をすり抜け | 高 | ログイン制限は**メール単位**のため「1パスワード×多数アカウント」のスプレーを数えられない。4xx 急増アラームは 5分で100件（≒20/分）で発火するため、**毎分十数回**に抑えると、メール単位制限・アラーム・スロットリングの全てを回避できる（`aws-architecture.md` §5.4 は IP 制限なしを受容しているが、この回避成立までは記載なし） |
| SEC2-04 | HS256 対称鍵のアプリ侵害時の全面波及 | 中 | API Lambda が署名鍵（`Jwt:Key`）と `OriginVerify` を同一シークレットで読むため、アプリに RCE が1つ入ると**任意ユーザーの JWT を偽造**でき、直接 API もなりすませる。1点侵害＝アプリデータ全面陥落（※閉域 VPC で外部持ち出しは封じられている点は緩和要素） |
| SEC2-05 | GitHub OIDC の信頼条件・サプライチェーン→本番 RCE | 高 | OIDC ロールは ECR への push と Lambda 更新ができる。信頼ポリシーの `sub` 条件が緩いとロールを奪取され、または依存ライブラリ・ベースイメージ・リポジトリの汚染が**そのまま本番 Lambda の RCE** になる |
| SEC2-06 | バックアップが同一アカウント・非イミュータブル | 中 | 自動バックアップ・スナップショットは同一アカウント内にあり、クロスアカウント/イミュータブルな退避がない。アカウント侵害時は**バックアップごと破壊**できる（破壊的攻撃・ランサムへの最終防衛線が弱い）。第1回・設計書は誤操作・障害は想定するが悪意は未想定 |
| SEC2-07 | 作業者 PC の一時ルート認証情報の窃取 | 中 | 作業者はルートユーザー＋`aws login` の一時認証情報で Terraform/CLI を実行する（`aws-architecture.md` §4.12 受容）。受容理由は「アクセスキーを作らない」ことだが、**一時認証情報が作業者 PC 上に最長12時間存在**し、情報窃取マルウェアに奪われるとアカウント全権になる点は未記載 |
| SEC2-08 | サブドメイン乗っ取り・DNS アカウントが信頼境界 | 中 | Amplify アプリ削除時に CNAME が残ると**サブドメイン乗っ取り**のリスク。ムームーDNS/レジストラのアカウントが侵害されると DNS 乗っ取り＋攻撃者による ACM 証明書取得で中間者化。外部 DNS が TCB に入る点が未記載 |
| SEC2-09 | 監査・改ざん検知・脅威検知の不足 | 中 | CloudTrail は既定のイベント履歴（90日）のみで、**S3 への専用証跡・ログ整合性検証・脅威検知（GuardDuty）がない**。SEC2-01〜03 の低速攻撃と相まって、侵害に気づけず後追いもできない可能性 |
| SEC2-10 | HttpOnly でも XSS でセッションライドが可能 | 低 | トークンは HttpOnly Cookie で JS から読めないが、XSS が発生すると同一オリジンから `/api/bff` を呼び、CSRF ヘッダーも自ら付けて**本人として全操作**できる。CSP は `'unsafe-inline'` 許容中（第1回 5.5 / §5.4 受容）のため、「アカウントは XSS から安全」とまでは言えない点を明示 |
| SEC2-11 | シークレット手動登録時の漏洩点 | 低 | Secrets Manager への値登録（`aws-architecture.md` 手順9）を CLI で行うと、`--secret-string` の値が**シェル履歴・クリップボード・コンソール**に残りうる。state に載せない配慮は徹底されているが、登録操作自体の漏洩が未記載 |

# 5. 対策方針（コスト最優先）

費用帯で3段階に分ける。**Tier 1・Tier 2 を採用**し、Tier 3 は「天井」として受容する（公開範囲拡大時に再検討）。

## 5.0 前提の是正：IP 対策は WAF なしで $0 で実装できる

`aws-architecture.md` §5.2 は「API Gateway からは送信元が全て BFF に見えるため IP 制限は WAF でしか行えない」と結論づけた。しかし **BFF（Amplify 上の Next.js）自身は CloudFront 経由の `x-forwarded-for` で実クライアント IP を参照できる**。したがって IP 単位のスプレー対策は、WAF（月約21ドル）を導入せず **BFF/API のコードで $0** で実装できる。これが本対策群の費用対効果の要である。

## 5.1 Tier 1（¥0：コード・Terraform 設定・運用）

| 対策 | 対応する盲点 | 概要 |
| --- | --- | --- |
| `X-Origin-Verify` の最前段検証＋強度チェック | SEC2-01, SEC2-02 | API の認証・DB アクセスより前のミドルウェアで検証し、不一致は即 403（DB/Auth を通さずコストを最小化）。起動時に `Jwt:Key` と同様の最小強度（32バイト以上）を検証 |
| `X-Origin-Verify` のローテーション対応 | SEC2-02 | API が「旧値＋新値」の2つを一時的に許可する実装にし、無停止ローテーション手順を文書化。生成は `openssl rand -base64 48` |
| ログイン制限に IP 単位＋全体合算を追加 | SEC2-03 | BFF が実クライアント IP を信頼ヘッダで API に転送し、既存 `LoginAttemptLimiter` に IP 単位とスプレー検知用の全体合算カウントを追加（既存と同じインメモリ方式で追加費用なし） |
| auth 系ルートのスロットリングを個別に低く設定 | SEC2-01, SEC2-03 | HTTP API のルート単位スロットリングで `/api/auth/*` を全体より低く設定 |
| OIDC 信頼ポリシーの厳格化 | SEC2-05 | `sub` を完全一致（`repo:toshiki24/task-management-system:ref:refs/heads/main`）、`aud` 条件も付与。ワークフローは `permissions:` 最小化、Actions をコミット SHA 固定 |
| CSP の nonce 方式への切替（準備） | SEC2-10 | コードは準備し、最終切替は Amplify で middleware 動作確認後（第1回 5.5 / §10 の残課題） |
| レジストラ/ムームーDNS の MFA＋CAA レコード | SEC2-08 | MFA を有効化。`CAA 0 issue "amazon.com"` を DNS に追加（Amplify 削除時は CNAME も削除する運用を明記） |
| シークレットの強度・登録手順 | SEC2-02, SEC2-11 | `openssl rand` で生成し、`--secret-string file://…` → `shred`、または `read -s` 経由で登録しシェル履歴に残さない |

## 5.2 Tier 2（月数百円：費用対効果が高い）

| 対策 | 対応する盲点 | 概要・費用目安 |
| --- | --- | --- |
| 専用 CloudTrail（管理イベント）を S3 へ＋ログ整合性検証 | SEC2-09 | 管理イベントの単一証跡は無料、S3 保管はこの規模で月数十円。侵害時の追跡能力が大きく向上 |

| ログイン 401 件数のメトリクスフィルタ＋アラーム | SEC2-03 | メトリクスフィルタは無料、アラームは1個 約$0.10/月。4xx 急増（100/5分）より低い閾値で低速スプレーを捕捉 |

# 8. 到達できるセキュリティ水準と残る天井

* **到達水準**：Tier 1・Tier 2（$0〜月数百円）で、SEC2-01〜SEC2-11 の高・中リスクのほぼ全てを、$0〜わずかな費用で**実務本番相当まで**引き上げられる。日和見攻撃・自動スキャン・ボット・一般的なパスワードスプレーに対しては堅牢になる。
* **$0 では超えられない天井（Tier 3）**：高度な L7/ボット攻撃（WAF）、アプリ単一侵害の全面波及（HS256 鍵分離）、AZ 障害（マルチAZ）、リアルタイム脅威検知（GuardDuty）。これらは設計思想（コスト優先・サーバーレス・HS256・WAF なし）に内在するもので、お金かアーキテクチャ変更が必要。公開範囲を広げる段階で再検討する。

# 付録A. SEC2-08 DNS・レジストラのハードニング手順

外部サービス（ムームードメイン／ムームーDNS、GMO）の画面操作が中心で、Terraform では管理しない。作業者が以下を実施する。

## A.1 レジストラ・DNS アカウントの MFA（今すぐ・AWS 不要）

* ムームードメイン（ムームーDNS）のアカウントに2段階認証（MFA）を有効化する。DNS を乗っ取られると、サブドメインの向き先変更や、攻撃者による証明書の取得（中間者化）につながるため、ドメイン管理アカウントは信頼境界に含まれる。
* AWS ルートユーザーの MFA は `aws-architecture.md` §4.12 で設定済み。

## A.2 CAA レコード（手順16：CNAME 追加と同時）

証明書を発行できる認証局を、意図した認証局だけに限定する。Amplify の証明書は ACM（Amazon）が発行するため `amazon.com` を許可する。

* **サブドメイン（`tms.accent24.jp`）にのみ** 設定する。親ドメイン `accent24.jp` には設定しない（親は既存サイトをロリポップで配信しており、別の認証局＝Let's Encrypt 等で証明書を更新している可能性があるため、親に制限をかけると既存サイトの証明書更新を妨げるおそれがある。CAA はドメインのノード単位で評価されるため、サブドメインにのみ置けば親に影響しない）。

  | ホスト | 種別 | 値 |
  | --- | --- | --- |
  | `tms`（= `tms.accent24.jp`） | `CAA` | `0 issue "amazon.com"` |

* 単一サブドメインのため `issuewild` は不要。違反通知用の `iodef` は任意（メールアドレスを公開リポジトリに残さないため本書には記載しない）。
* **注意**：ムームーDNS の「カスタム設定」で CAA レコードが追加できるか確認する。対応していない場合は、CAA なしで運用する（ACM の発行自体は CAA が無くても成功する）か、対応する DNS への移行を検討する。**親ドメインに広く効く CAA は設定しない**（既存サイトの証明書更新を壊さないため）。
* ACM の DNS 検証用 CNAME は CAA では妨げられない（CAA は発行を制限するだけ）。`amazon.com` を許可していれば ACM は発行できる。

## A.3 サブドメイン乗っ取りの防止（テアダウン運用）

サブドメインが Amplify を指す CNAME を残したまま Amplify アプリを削除すると、第三者が同名の向き先を取得してサブドメインを乗っ取れる（dangling CNAME）。

* **Amplify アプリを削除する際は、ムームーDNS のアプリ用 CNAME（および ACM 検証用 CNAME）を同時に削除する。**
* `aws-architecture.md` 6.3 の「環境をすべて削除する（`terraform destroy`）」を行う場合の手順に、この CNAME 削除を含める。

## A.4 デプロイ後の確認

* `https://tms.accent24.jp` の証明書が ACM（Amazon）発行であることを確認する。
* `dig CAA tms.accent24.jp`（または同等）で、`0 issue "amazon.com"` が返ることを確認する（CAA を設定した場合）。
* 親ドメインの既存サイト（ロリポップ）の表示と証明書に影響がないことを確認する。
