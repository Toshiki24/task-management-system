# Phase 2 M5 基本設計: 見える化・運用・エンタープライズ

Phase 2 のマイルストーン M5 の基本設計。M1〜M4 で「チームで速く正しく協働し、Git とタスクが連動する」状態になった上に、**開発の見える化（指標ダッシュボード）**、**運用（自己ホスト配布・可観測性・インポート/エクスポート）**、**エンタープライズ（管理コンソール・MFA・SSO）** を載せる。到達目標の M1〜M4 は完了済みで、M5 は余力に応じて着手する位置づけ（要件 §10）。

- 関連: [Phase 2 要件定義](../../docs/phase2/requirements.md)（§5.9 見える化・§5.10 管理/監査・§6 UX・§8 運用形態・§9 非機能・§10） / [M1 基本設計](./m1-workspace.md) / [M4 基本設計](./m4-git-integration.md)
- 前提（M1〜M4 で確定済み）: 認可は 3 スコープ（System/Workspace/Project）に集約（`ProjectAccess` / `WorkspaceAccess`）、非所属は 404。データアクセスは**生 SQL を使わず EF Core LINQ**。監査は `audit_logs`、活動は `activities`、Git リンクは `task_git_links`、状態履歴は `task_status_histories`。スキーマ変更はマージ後にマイグレーション用 Lambda を手動実行。本番は AWS（API Gateway+Lambda / Amplify / RDS）、秘密は Secrets Manager。

> **ステータス: 📝 基本設計（実装はこれから）**。本書で方針を固め、M2〜M4 と同じく §13 のステップを PR 単位（各 PR で UT/E2E グリーン）で実装する。SSO(SAML/OIDC) や Helm など重量級・外部依存の大きい項目は、ポートフォリオの検証可能性を踏まえ段階的に扱う（§12 に判断を明記）。

## 1. 目的と範囲

M4 までで機能はそろった。M5 は **「状況が数字で見える」「自社で運用できる」「組織の要件（認証・監査）に応える」** を載せる。

M5 で作るもの（優先度順）：

- **開発指標・ダッシュボード**：進捗（状態別件数・完了率）、担当別の負荷、期限超過、**サイクルタイム / スループット / リードタイム**（タスクの状態履歴・Git リンクから算出）
- **インポート/エクスポート**：タスクの CSV エクスポート／インポート（他ツール移行・バックアップ）
- **管理コンソール（System Admin）**：全ワークスペース・全ユーザーの一覧、System Admin 権限付与/剥奪、監査ログ閲覧、システム統計
- **MFA（TOTP）**：任意有効化の多要素認証（認証アプリ）
- **SSO（OIDC/SAML）**：外部 IdP 連携（§7・§12 の判断に沿って段階的に）
- **自己ホスト配布**：Docker Compose で AWS 非依存に起動できる構成（Helm は将来）
- **可観測性**：構造化ログ・ヘルスチェック・主要メトリクスの出力

### 範囲外（M5 では作らない）

- SCIM プロビジョニング（将来を見据えた設計に留める）
- 高度な BI（外部 BI ツール連携）。本アプリ内の基本ダッシュボードに限定
- マルチテナント化（方針どおり 1 インスタンス=1 組織）

## 2. 開発指標・ダッシュボード

既存データから集計する。**新規の重いデータ収集は行わず**、`tasks` / `task_status_histories`（状態遷移の履歴）/ `activities` / `task_git_links` から導出する。

### 2.1 指標の定義

| 指標 | 定義 | 元データ |
| --- | --- | --- |
| 進捗 | 状態カテゴリ別の件数・完了率 | `tasks.status` × `workflow_states.category` |
| 担当別の負荷 | 担当者ごとの未完了件数・見積合計 | `tasks.assignee_id` / `estimate_points` |
| 期限超過 | 期日を過ぎた未完了件数 | `tasks.due_date` |
| **サイクルタイム** | 「進行中(IN_PROGRESS)に入った時刻」→「完了(DONE)に入った時刻」の所要時間 | `task_status_histories` |
| **スループット** | 期間内に完了(DONE)へ遷移した件数 | `task_status_histories` |
| **リードタイム** | 作成→完了の所要時間 | `tasks.created_at` / `task_status_histories` |

- 集計は **LINQ で DB 側に寄せる**（SQL 生成は EF に任せる）。重い集計は期間・プロジェクトで絞る。
- 可視性は 3 スコープに従う：ワークスペース/プロジェクトのダッシュボードは、その所属メンバーのみ（`WhereVisibleTo` と同じ原則）。System Admin はインスタンス全体の統計を見られる。
- 時系列（スループットの推移等）は日次バケットで返す。グラフ描画はフロント。

### 2.2 算出方針（履歴の扱い）

- サイクル/リードタイムは `task_status_histories` の遷移時刻から、タスク単位に「初めて IN_PROGRESS に入った時刻」「初めて/最後に DONE に入った時刻」を取り出して差分する。
- 履歴が無い過去タスクは対象外（データのある範囲で算出）とし、欠損は件数に出さない。

## 3. データモデル

M5 は既存データからの集計が中心で、**新規テーブルは最小限**にする。

| 区分 | テーブル/カラム | 役割 |
| --- | --- | --- |
| 追加 | `user_mfa`（または `users` へ列追加） | TOTP シークレット（暗号化参照）・有効化状態・リカバリコード |
| 追加 | `sso_connections` | IdP 接続設定（OIDC/SAML・issuer・メタデータ参照）。資格情報は Secrets Manager |
| 変更 | なし（指標・エクスポートは既存テーブルから導出） | — |

- 指標・インポート/エクスポート・管理コンソールは**スキーマ追加不要**（既存 `tasks` / `task_status_histories` / `audit_logs` / `workspaces` / `users` を使う）。
- MFA/SSO はそれぞれのステップで最小のテーブルを足す。TOTP シークレットや IdP クライアントシークレットは **DB 平文に置かず**、Secrets Manager/外部シークレット参照（M4 の `ISecretStore` を再利用）。

## 4. インポート/エクスポート

- **エクスポート**：プロジェクトのタスクを CSV で出力（`GET /api/projects/{id}/tasks/export.csv`）。CanView。列はタイトル・状態・担当・優先度・期限・見積・ラベル。文字コードは UTF-8(BOM 付き、Excel 対応)。生成はストリーミングで、巨大プロジェクトでもメモリを圧迫しない。
- **インポート**：CSV からタスクを一括作成（`POST /api/projects/{id}/tasks/import`）。CanWrite。1 行＝1 タスク。ヘッダ検証・1 件ずつのバリデーション・**行単位のエラー報告**（取り込めた件数と失敗行）。状態/担当/ラベルは既存の検証（WS のワークフロー・メンバー・ラベル）を通す。
- 冪等性は求めない（取り込みは明示操作）。巨大ファイルは上限件数で制限。

## 5. 管理コンソール（System Admin）

既存の System Admin 権限（M1）を活かし、運用画面を足す。すべて **System Admin 限定**、操作は `audit_logs` に記録。

- 全ワークスペース一覧（名前・メンバー数・プロジェクト数・作成日）
- 全ユーザー一覧（メール・作成日・System Admin フラグ・MFA 有効/無効）
- **System Admin 権限の付与/剥奪**（既存の監査アクション `user.system_admin.granted/revoked` を使用）
- **監査ログ閲覧**（フィルタ：アクター・アクション・対象・期間。ページング）
- システム統計（WS/プロジェクト/タスク/ユーザーの総数、直近のアクティビティ数）

## 6. MFA（多要素認証）

- 方式：**TOTP**（認証アプリ。SMS は使わない）。任意有効化。
- フロー：有効化時にシークレットを生成 → QR（otpauth URI）を表示 → ユーザーがコード入力で確認 → **リカバリコード**を発行。以降のログインでコードを要求。
- 保管：TOTP シークレットは暗号化/シークレットストア参照で保持し、DB 平文に置かない。リカバリコードはハッシュ化保存（パスワードと同方針）。
- 認証：既存のログイン（BFF＋リフレッシュトークン）に「MFA 検証」ステップを追加。MFA 有効ユーザーは一次認証後に TOTP を要求。
- 無効化・リカバリコード再発行は本人のみ。

---

## 7. SSO（SAML/OIDC）

- 方式：まず **OIDC**（実装・検証が比較的容易）。SAML は後続。SCIM は対象外（将来を見据えた設計に留める）。
- モデル：`sso_connections`（issuer・client_id・スコープ、client_secret は Secrets Manager 参照）。
- フロー：IdP の Authorization Code Flow。コールバックでユーザーをメールで突合（なければ招待済みのみ許可するか、自動プロビジョニングの可否を設定）。
- 既存のセッション（BFF/リフレッシュトークン）に合流させる。IdP ログアウト連携は任意。
- 外部 IdP への実接続はポートフォリオ環境では検証が難しいため、**抽象（`ISsoProvider`）＋ OIDC ディスカバリのパース等、ネットワークに出ない部分を単体テスト**し、実接続は設定とドキュメントで担保する（M4 の実アダプタと同じ方針）。

---

## 8. 自己ホスト配布（Docker Compose / Helm）

- **Docker Compose**：アプリ（API）＋フロント/BFF＋PostgreSQL を 1 コマンドで起動できる構成。設定は環境変数、秘密は `.env`/外部シークレット、マイグレーションは起動時またはワンショットで適用。ヘルスチェック・バックアップ/リストア手順・アップグレード手順を README 化。
- **Helm**：Kubernetes 向けチャートは将来（§15）。
- AWS 非依存を担保するため、Secrets Manager 依存部は `ISecretStore` の別実装（環境変数/ファイル）で差し替えられるようにする（M4 で導入済みの抽象を活用）。

## 9. 可観測性

- 構造化ログ（リクエスト ID・ユーザー/WS コンテキストを付与。秘密は出さない）。
- ヘルスチェック（`/health` の拡充：DB 接続・マイグレーション状態）。
- 主要メトリクス（リクエスト数・エラー率・レイテンシ、ジョブ実行結果）を CloudWatch/標準出力へ。
- 既存の監査ログ（`audit_logs`）と活動（`activities`）を運用の一次情報として位置づける。

## 10. API 設計の変更

| 区分 | エンドポイント | 認可 |
| --- | --- | --- |
| 指標 | `GET /api/projects/{id}/metrics`、`GET /api/workspaces/{id}/metrics`、`GET /api/admin/metrics` | CanView / WS メンバー / System Admin |
| エクスポート | `GET /api/projects/{id}/tasks/export.csv` | CanView |
| インポート | `POST /api/projects/{id}/tasks/import` | CanWrite |
| 管理 | `GET /api/admin/workspaces`、`GET /api/admin/users`、`GET /api/admin/audit-logs`、`GET /api/admin/stats` | System Admin |
| MFA | `POST /api/me/mfa/setup`、`POST /api/me/mfa/verify`、`DELETE /api/me/mfa`、ログイン時の MFA 検証 | 本人 |
| SSO | `GET/POST /api/admin/sso-connections`、`/api/auth/sso/{id}/start`・`/callback` | System Admin / 公開(コールバック) |

- 既存 DTO は原則据え置き、指標は専用の集計 DTO を返す（完全一致アサートの方針を維持）。

## 11. 画面への影響

- **ダッシュボード**：プロジェクト/ワークスペースの指標（進捗・負荷・期限超過・サイクル/リード/スループット）。グラフ（棒・折れ線）はアクセシブルに実装。
- **タスク一覧**：CSV エクスポート/インポートの導線。
- **管理コンソール**：System Admin 向けの新規画面（WS/ユーザー/監査ログ/統計）。
- **アカウント設定**：MFA の有効化/無効化、リカバリコード。
- すべて日本語ラベル。空状態・ローディング・エラー表示を備える。

---

## 12. 認可・セキュリティ

- 3 スコープ認可を踏襲：プロジェクト/WS 指標は所属メンバー、管理系は System Admin、MFA は本人。非所属は 404。
- 秘密情報（TOTP シークレット・SSO クライアントシークレット）は **Secrets Manager/外部シークレット参照**（`ISecretStore` 再利用）、DB 平文禁止。
- 監査：System Admin の操作・MFA 有効化/無効化・SSO 設定変更・インポートを `audit_logs` に記録。
- エクスポート/インポートは可視性・権限の範囲内のみ。CSV インジェクション対策（先頭の `=,+,-,@` をエスケープ）。
- 既存のセキュリティ（BFF・CSP nonce・レート制限・最小権限）を維持。

## 13. 実装順序（M5 内の分解）

各ステップを単体で完成・デモ可能な PR にし、UT/E2E をグリーンにしてマージ（M1〜M4 と同じ）。既存データから作れて検証しやすいものを先に、外部依存の大きいものを後に。

1. **指標ダッシュボード（基礎）**：進捗・担当別負荷・期限超過の集計 API＋画面
2. **開発指標（サイクル/リード/スループット）**：`task_status_histories` からの算出＋時系列、グラフ
3. **CSV エクスポート**：プロジェクトのタスク出力（ストリーミング・CSV インジェクション対策）
4. **CSV インポート**：行単位バリデーション・エラー報告
5. **管理コンソール**：全 WS/ユーザー一覧・監査ログ閲覧・統計・System Admin 付与/剥奪（UI）
6. **MFA（TOTP）**：有効化/検証/リカバリコード、ログインへの組み込み
7. **自己ホスト（Docker Compose）**：AWS 非依存の起動構成・手順書
8. **可観測性**：構造化ログ・ヘルスチェック拡充・メトリクス
9. **（任意）SSO（OIDC）**：抽象＋ディスカバリのパース（テスト可能部）＋設定・ドキュメント
10. 各ステップのテスト（可視性・認可・集計の正しさ・境界条件を重点）

## 14. テスト方針

- **単体（xUnit）**：指標集計（状態履歴からのサイクル/リード/スループット、境界・欠損）、CSV 生成/パース（インジェクション対策含む）、管理系の認可（System Admin 限定・非 Admin 403/404）、MFA（TOTP 検証・リカバリコード）、SSO のディスカバリパース。外部ネットワークに出る部分はフェイクで差し替える。
- **E2E（Playwright）**：API（指標・エクスポート/インポート・管理コンソール・MFA）と画面（ダッシュボード表示・CSV 導線・管理画面・MFA 設定）。実 DB（Postgres）で検証。
- M2〜M4 で確立した方針（完全一致アサート維持・Fake による非ネットワーク化・PR 単位グリーン）を踏襲する。

## 15. 未決事項

- **SSO/SAML の実検証**：外部 IdP が必要なため、ポートフォリオでは OIDC のテスト可能部＋設定・手順に留めるか、モック IdP を用意するか。
- **Helm チャート**：Docker Compose を優先し、Helm は需要を見て判断。
- **MFA 必須化ポリシー**：WS 単位で MFA 必須にできるようにするか（初期は任意のみ）。
- **指標の保持**：都度集計で足りるか、負荷が見えたら集計結果のキャッシュ/日次スナップショットを足すか。
- **エクスポート範囲**：タスク以外（コメント・活動・Git リンク）の出力やワークスペース全体エクスポートを含めるか。
