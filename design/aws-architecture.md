# 2. 目的と前提

## 2.1 目的

本番環境を AWS に構築するための構成・設定値・運用方法と、その設計判断の理由を定める。Terraform のコード（`infra/terraform/`）は本書に基づいて作成する。Terraform の使い方は `infra/terraform/README.md` を参照する。

## 2.2 設計方針

要件定義書 13.3「可能な限り低コストで運用できる構成」、19章「AWSの利用料金を抑える」「ポートフォリオ用途として必要な基本対策を実施する」を踏まえ、以下の方針とする。

| 方針 | 内容 |
| --- | --- |
| セキュリティ | 秘密情報をリポジトリ・環境変数・Terraform の state・ビルド成果物に置かない。DB をインターネットに公開しない。IAM は必要最小限の権限とする。人がアクセスキーを持つ場所を最小にする |
| コスト | 常時課金のリソース（NAT ゲートウェイ、複数AZのDB、パブリックIPv4アドレス、WAF等）を避け、利用量課金のサーバーレス（Lambda、API Gateway、Amplify）を中心にする。月額の目安は約30〜40ドル（6章） |
| 可用性 | 要件定義書 8.2・基本設計書 19.2 に基づき、マネージドサービスで個人開発規模の可用性を確保する。複数AZの冗長化はコストのため行わず、バックアップからの復旧で対応する |
| 保守性 | すべてのリソースを Terraform で管理する（AWS・外部サービスの画面操作が必要なものを除く）。手動の作業は9章に明記する |

## 2.3 用語

| 用語 | 意味 |
| --- | --- |
| 秘密情報 | 漏洩すると不正利用につながる値。パスワード、署名鍵（`Jwt:Key`）、Cookieの暗号化鍵（`SESSION_SECRET`）、パスワードを含むDB接続文字列、BFFとAPIで共有する秘密情報（`X-Origin-Verify` の値）、JWT、Cookie 等（要件定義書 14章・基本設計書 17章の「秘密情報」と同じ） |
| 秘密情報ではない設定値 | 公開されても不正利用につながらない設定値。APIのURL（`API_BASE_URL`）、シークレットの名前（`APP_SECRET_ID` 等）等 |
| シークレット | Secrets Manager に秘密情報を保存する単位（例：API用シークレット） |

# 3. 全体構成

```text
                        ┌────────────────────── AWS（東京リージョン ap-northeast-1）──────────────────────┐
                        │                                                                              │
ブラウザ ──HTTPS──▶ Amplify Hosting（tms.accent24.jp）                                                   │
  ▲  HttpOnly Cookie    │  Next.js（画面 ＋ BFF）── SSR 実行ロール ──▶ Secrets Manager（BFF用シークレット） │
  │                     │        │                                                                      │
  │                     │        │ HTTPS（Authorization: Bearer {JWT}、X-Origin-Verify）                 │
  │                     │        ▼                                                                      │
  │                     │  API Gateway（HTTP API、スロットリング）                                        │
  │                     │        │                                                                      │
  │                     │        ▼                                                                      │
  │                     │  ┌──────────── VPC（プライベートサブネットのみ、インターネット接続なし）────────┐  │
  │                     │  │  Lambda（API、コンテナイメージ）──5432──▶ RDS for PostgreSQL（1AZ）      │  │
  │                     │  │        │ 443                                                          │  │
  │                     │  │        ▼                                                              │  │
  │                     │  │  VPC エンドポイント ──▶ Secrets Manager（API用シークレット、RDSのパスワード） │  │
  │                     │  └───────────────────────────────────────────────────────────────────────┘  │
  │                     │  ECR（コンテナイメージ）  CloudWatch（ログ・アラーム）  SNS（通知メール）            │
  │                     └──────────────────────────────────────────────────────────────────────────────┘
  │
ムームーDNS（親ドメイン）：アプリ用のサブドメイン → Amplify（CNAME）、親ドメイン → ロリポップ（既存のサイト）
```

| 通信経路 | プロトコル | 認証・保護 |
| --- | --- | --- |
| ブラウザ → Amplify | HTTPS | セッションCookie（HttpOnly / Secure / SameSite=Lax）、CSRF対策（API詳細仕様書 6.3） |
| Amplify（BFF）→ API Gateway | HTTPS | JWT（アクセストークン）、BFFからの通信であることを示す共有の秘密情報（`X-Origin-Verify`、5.3） |
| API Gateway → Lambda | AWS 内部 | API Gateway にのみ Lambda の呼び出しを許可（リソースベースポリシー） |
| Lambda → RDS | PostgreSQL（TLS必須） | VPC 内のみ。セキュリティグループで Lambda からのみ許可。アプリ専用のDBユーザー |
| Lambda → Secrets Manager | HTTPS（VPC エンドポイント経由） | 実行ロールで対象のシークレットのみ読み取り可 |
| Amplify（BFF）→ Secrets Manager | HTTPS | SSR 実行ロールで対象のシークレットのみ読み取り可 |

ブラウザが直接通信するのは Amplify のみであり、API Gateway・RDS へは直接アクセスしない（基本設計書 3.2）。

# 4. リソース設計

## 4.1 リージョン・命名・タグ

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| リージョン | 東京（`ap-northeast-1`） | 利用者・開発者が日本にいるため。使用するすべてのサービスが利用できる |
| 環境 | 本番（`prod`）のみ | ポートフォリオ用途のため。開発・テストはローカル環境と CI で行う |
| 命名 | `task-management-system-prod-{用途}`（例：`task-management-system-prod-db`） | 既存のリソースと区別するため |
| タグ | `Project=task-management-system`、`Environment=prod`、`ManagedBy=terraform` | 既存のリソースとの区別、請求画面でのこのアプリの費用の確認（Terraform の `default_tags` で全リソースに付与） |

## 4.2 ネットワーク

| リソース | 設定 | 理由 |
| --- | --- | --- |
| VPC | `10.0.0.0/16` | |
| プライベートサブネット | `10.0.1.0/24`（`ap-northeast-1a`）、`10.0.2.0/24`（`ap-northeast-1c`） | RDS のサブネットグループには2つのAZのサブネットが必要なため。Lambda も両方に配置する |
| パブリックサブネット | 作成しない | インターネットから到達できる場所を作らない |
| インターネットゲートウェイ・NAT ゲートウェイ | 作成しない | VPC 内のリソースはインターネットに出る必要がない。NAT ゲートウェイは月45ドル以上かかる |
| VPC エンドポイント（インターフェース型） | Secrets Manager 用。`ap-northeast-1a` のサブネットのみ | Lambda が VPC 内から Secrets Manager を読むため。Secrets Manager は起動時にのみ読むため1AZで十分（1AZあたり月約10ドル） |

Lambda のログ出力（CloudWatch Logs）とコンテナイメージの取得（ECR）は Lambda サービス側で行われるため、VPC エンドポイントは不要である。

**セキュリティグループ**

| セキュリティグループ | インバウンド | アウトバウンド |
| --- | --- | --- |
| Lambda 用 | なし | RDS 用へ TCP 5432、VPC エンドポイント用へ TCP 443 |
| RDS 用 | Lambda 用から TCP 5432 | なし |
| VPC エンドポイント用 | Lambda 用から TCP 443 | なし |

送信元・送信先は IP アドレスではなくセキュリティグループで指定し、Lambda 以外から RDS・VPC エンドポイントに接続できないようにする。

## 4.3 RDS（PostgreSQL）

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| エンジン | PostgreSQL 16（最新のマイナーバージョン） | ローカル環境（`postgres:16-alpine`）と同じメジャーバージョン |
| インスタンスクラス | `db.t4g.micro` | 最小・最安。想定する規模（要件定義書 19章「大規模アクセスは想定しない」）に十分 |
| ストレージ | gp3、20GB、自動拡張なし | 最小容量。想定外の増加による課金を防ぐ（空き容量はアラームで監視、4.10） |
| 配置 | シングルAZ | マルチAZは費用が約2倍。可用性はバックアップからの復旧で確保する（7章） |
| パブリックアクセス | 無効 | DB をインターネットに公開しない |
| 保存時の暗号化 | 有効（AWS 管理キー） | 追加費用なし |
| 通信の暗号化 | TLS を必須にする（`rds.force_ssl=1`、接続文字列 `SSL Mode=Require`） | |
| マスターユーザーのパスワード | RDS が Secrets Manager で管理する（`manage_master_user_password = true`） | パスワードを Terraform の state に残さない。定期的なローテーションも RDS が行う |
| アプリ用のDBユーザー | マスターユーザーとは別に、アプリ専用のユーザー（`tms_app`）を作成し、アプリのテーブルの参照・更新のみを許可する | 最小権限。マスターユーザーのパスワードのローテーションの影響を受けないようにする |
| 自動バックアップ | 7日間（ポイントインタイムリカバリ有効） | 誤操作・障害からの復旧のため |
| 削除保護 | 有効。削除時は最終スナップショットを取得する | `terraform destroy` 等による誤削除を防ぐ |
| マイナーバージョンの自動更新 | 有効（メンテナンスウィンドウ：日曜 3:00〜4:00 JST） | セキュリティ修正を適用するため |
| 拡張モニタリング・Performance Insights | 無効 | 費用を抑えるため。基本的なメトリクスは CloudWatch で確認できる |

**接続数の上限**：`db.t4g.micro` の最大接続数は約80〜110と少ないため、接続文字列で1インスタンスあたりの接続プールを `Maximum Pool Size=5` に制限し、Lambda の同時実行数の上限（4.4）と合わせて、接続数の上限を超えないようにする。

## 4.4 Lambda

| 項目 | API用 | マイグレーション用 |
| --- | --- | --- |
| 用途 | バックエンドAPI（ASP.NET Core） | DB のマイグレーション（EF Core）とアプリ用DBユーザーの作成を手動で実行する |
| パッケージ | コンテナイメージ（`backend/Dockerfile`、ECR） | API 用と同じイメージ（実行するコマンドのみ変える） |
| アーキテクチャ | x86_64 | 同左 |
| メモリ | 1024MB | 1024MB |
| タイムアウト | 30秒（API Gateway の統合タイムアウトの上限） | 5分 |
| 同時実行数の上限 | 10（予約済み同時実行） | 1 |
| 配置 | VPC 内（プライベートサブネット2つ）、Lambda 用のセキュリティグループ | 同左 |
| 環境変数 | `APP_SECRET_ID`（API用シークレットの名前）、`ASPNETCORE_ENVIRONMENT=Production` | `APP_SECRET_ID`、RDS のマスターユーザーのシークレットの名前 |
| 呼び出し元 | API Gateway のみ（リソースベースポリシー） | 作業者が手動で実行（`aws lambda invoke`） |

**同時実行数の上限を設ける理由**：大量のリクエストによる Lambda・RDS の費用の増加（コストを狙った攻撃）と、RDS の接続数の枯渇を防ぐ。

**コールドスタート**：VPC 内の .NET の Lambda は、しばらく使われなかった後の最初のリクエストで数秒かかる。常に起動しておく設定（プロビジョニング済み同時実行）は常時課金になるため使わず、ポートフォリオ用途として許容する。

## 4.5 API Gateway

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| 種類 | HTTP API | REST API より安く、Lambda との統合が簡単。WAF・使用量プランは BFF 構成では不要（5.2） |
| ルート | `$default` → API用 Lambda（ペイロード形式 2.0） | ルーティングは ASP.NET Core が行う |
| エンドポイント | API Gateway の既定のURL（`https://{api-id}.execute-api.ap-northeast-1.amazonaws.com`）。これに `/api` を付けたものを BFF の `API_BASE_URL` とする（API詳細仕様書 3.1） | ブラウザから直接呼び出さないため、カスタムドメインは不要 |
| CORS | 設定しない | ブラウザから直接呼び出さないため（API詳細仕様書 6.3） |
| スロットリング | ステージ全体で 毎秒20リクエスト、バースト40 | 大量のリクエストによる費用の増加・負荷を防ぐ（5.2） |
| アクセスログ | CloudWatch Logs に JSON で出力（リクエストID、送信元IP、メソッド、パス、ステータス、処理時間）。ヘッダー・本文は出力しない | 障害調査のため。JWT 等の秘密情報を記録しない（基本設計書 18章） |

## 4.6 ECR

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| リポジトリ | `task-management-system-api` | |
| イメージタグ | 変更不可（IMMUTABLE）。Git のコミットハッシュをタグにする | デプロイしたイメージを後から差し替えられないようにする。どのコミットのイメージか分かるようにする |
| 脆弱性スキャン | プッシュ時に基本スキャンを実行 | 無料 |
| ライフサイクルポリシー | 最新の10個を残して削除 | 保存容量の課金を抑える。ロールバック用に直近のイメージは残す |

## 4.7 Amplify Hosting

| 項目 | 設定 | 理由 |
| --- | --- | --- |
| プラットフォーム | SSR（`WEB_COMPUTE`） | BFF（Route Handler）がサーバー側で動作する必要があるため（セキュリティ見直し記録 6.2） |
| リポジトリ・ブランチ | GitHub の `main` ブランチ。プッシュ時に自動でビルド・デプロイする | |
| アプリのルート | `frontend`（モノレポ） | |
| Node.js | 24 系（ビルド設定で `nvm use 24`） | 基本設計書 4.1 |
| プレビュー環境（プルリクエストごとの環境） | 作成しない | 公開される環境を増やさない。テストは CI で行う |
| カスタムドメイン | `tms.accent24.jp`。証明書は Amplify が管理（ACM） | 4.11 |
| SSR 実行ロール（compute role） | BFF用シークレットの読み取りのみ許可 | `SESSION_SECRET` を実行時に Secrets Manager から読むため |
| 環境変数 | `API_BASE_URL`（秘密ではない）、`BFF_SECRET_ID`（BFF用シークレットの名前） | 秘密情報そのものは環境変数に置かない |
| GitHub との連携 | Amplify GitHub App を作業者がコンソールで許可する | GitHub のアクセストークンを Terraform の変数・state に置かない |
| WAF | 導入しない（5.2） | 連携料だけで月15ドルかかるため |

**環境変数の扱い**：Amplify Hosting の SSR では、コンソールで設定した環境変数はビルド時にのみ参照でき、実行時には自動では渡らない。そのため、ビルド設定（`amplify.yml`）で秘密情報ではない設定値（`API_BASE_URL`、`BFF_SECRET_ID`）のみを `.env.production` に書き出す。秘密情報（`SESSION_SECRET`）は書き出さず、BFF が実行時に SSR 実行ロールで Secrets Manager から読み込む。

## 4.8 Secrets Manager

| シークレット | 内容（JSONのキー） | 読み取るもの | 値の登録 |
| --- | --- | --- | --- |
| `task-management-system/prod/api` | `Jwt:Key`（32バイト以上）、`ConnectionStrings:DefaultConnection`（アプリ用DBユーザー、`SSL Mode=Require`、`Maximum Pool Size=5`）、`OriginVerify:Secret` | API用 Lambda | 作業者が手動で登録 |
| `task-management-system/prod/bff` | `SESSION_SECRET`（32文字以上）、`ORIGIN_VERIFY_SECRET`（API用と同じ値） | Amplify の SSR 実行ロール | 作業者が手動で登録 |
| RDS が管理するシークレット | マスターユーザーのユーザー名・パスワード | マイグレーション用 Lambda | RDS が自動で作成・ローテーション |

* Terraform はシークレットの**入れ物のみ**を作成し、値は作業者が AWS CLI またはコンソールで登録する。秘密情報を Terraform のコード・変数・state に含めないため（`infra/terraform/README.md`）。
* 値は `openssl rand` 等で十分な長さのランダムな文字列を生成する。
* API は起動時に `APP_SECRET_ID` のシークレットを設定として読み込む（基本設計書 3.2、`Configuration/SecretsManagerConfiguration.cs`）。
* 値を変更した場合は、API用 Lambda の再デプロイ（またはコールドスタート）後に反映される。`Jwt:Key` を変更すると発行済みのアクセストークンが、`SESSION_SECRET` を変更すると全ユーザーのセッションが無効になる。

## 4.9 IAM

| ロール・ユーザー | 許可する操作 | 備考 |
| --- | --- | --- |
| API用 Lambda の実行ロール | VPC 内での実行（ネットワークインターフェースの作成等）、CloudWatch Logs への出力、API用シークレットの読み取り | 他のシークレット・サービスへのアクセスは許可しない |
| マイグレーション用 Lambda の実行ロール | 上記に加え、RDS が管理するマスターユーザーのシークレットの読み取り | |
| Amplify の SSR 実行ロール | BFF用シークレットの読み取り | |
| Amplify のサービスロール | Amplify のビルド・デプロイ、CloudWatch Logs への出力 | Amplify が使用する |

## 5.2 IP 単位のレート制限（セキュリティ見直し記録 5.2・8章の見直し）

セキュリティ見直し記録では、パスワードスプレー（多数のアカウントに同じパスワードを試す攻撃）への対策として「API Gateway のスロットリング、または AWS WAF のレートベースルール（IP単位）」を想定していた。しかし BFF 構成では、**API Gateway から見た送信元はすべて Amplify（BFF）になる**ため、API Gateway・WAF で利用者の IP 単位に制限することはできない。利用者の IP で制限できるのは、利用者から直接リクエストを受ける Amplify の前段のみである。

| 案 | 費用 | 評価 |
| --- | --- | --- |
| Amplify に AWS WAF を適用し、ログインのパスにレートベースルールを設定する | 月約21ドル以上（Amplify との連携料15ドル、Web ACL 5ドル、ルール1ドル、リクエスト数に応じた料金） | IP 単位で制限できるが、全体の費用が約1.6倍になる |
| API Gateway のスロットリング（ステージ全体） | 無料 | IP 単位ではないが、全体のリクエスト数を制限し、総当たりの速度と費用の増加を抑えられる |
| アプリのメールアドレス単位の制限（実装済み） | 無料 | 同じアカウントへの総当たりを防げる |

**判断**：WAF は導入せず、API Gateway のスロットリング、Lambda の同時実行数の上限、アプリのメールアドレス単位の制限、API Gateway の 4xx の急増のアラームを組み合わせる。パスワードスプレーへの IP 単位の対策がないことはリスクとして受容する。

**受容する理由**：ポートフォリオ用途で利用者が限られること、スロットリングにより試行の速度が制限されること、パスワードはBCryptでハッシュ化されていること。

**見直しの条件**：公開範囲を広げる場合、または 4xx の急増のアラームが繰り返し発生した場合は、Amplify への WAF の適用を再検討する。

## 5.3 API への直接アクセスの制限（セキュリティ見直し記録 8章の対応）

API Gateway のURLは公開されており、BFF を経由せずに直接呼び出すことができる。JWT による認証・認可は API 側で行っているため、直接呼び出されても認証をすり抜けることはないが、BFF の CSRF 対策・セッション管理を経由しない呼び出しや、ログインAPIへの直接の総当たりを防ぐため、以下を行う。

* BFF は、API へのすべてのリクエストに共有の秘密情報のヘッダー `X-Origin-Verify` を付ける。
* API は、ヘッダーの値が Secrets Manager の `OriginVerify:Secret` と一致しないリクエストを 403 で拒否する（比較は処理時間が値に依存しない方法で行う）。

| 採用しなかった案 | 理由 |
| --- | --- |
| API Gateway のリソースポリシーで送信元IPを制限する | HTTP API ではリソースポリシーを使えない。また Amplify の SSR の送信元IPは固定されていない |
| IAM 認証（BFF が SigV4 で署名する） | 最も強固だが、BFF に署名の処理が必要になり実装が複雑になる。共有の秘密情報で十分と判断した |

## 5.4 受容するリスク

| リスク | 受容する理由 | 見直しの条件 |
| --- | --- | --- |
| パスワードスプレーへの IP 単位の対策がない | 5.2 | 5.2 |
| RDS がシングルAZのため、AZ障害時に停止する | ポートフォリオ用途で、停止による影響が小さい。費用が約2倍になる | 本番運用として利用する場合 |
| CSP の `script-src` に `'unsafe-inline'` を許可している | セキュリティ見直し記録 5.5 | Amplify で Next.js の middleware が動作することを確認できた場合（10章） |
| アプリのログイン試行回数の制限は Lambda のインスタンスごと（メモリ上）で共有されない | セキュリティ見直し記録 5.2。同時実行数の上限（10）により影響は限定的 | 利用者が増えた場合 |

# 11. 設計判断と採用しなかった案

| 検討事項 | 採用した案 | 採用しなかった案と理由 |
| --- | --- | --- |
| アプリの公開URL | サブドメイン（`tms.accent24.jp`） | 親ドメインのパス（`/{パス}`）：ドメイン全体の前段に CloudFront を置き、既存のサイトの配信経路・DNS を変更する必要がある。既存のサイトと同じオリジンになり、既存のサイトのスクリプトやXSSからアプリの BFF を本人として呼び出せる、HSTS（`includeSubDomains`）やCookie が互いに影響する。Next.js の `basePath` への対応も必要になる |
| DNS | ムームーDNS に CNAME を追加 | Route 53 にサブドメインを委任：API にカスタムドメインを使わないため不要 |
| API の実行環境 | Lambda（コンテナイメージ） | ECS Fargate・App Runner：常時起動のため、アクセスがなくても費用がかかる。Lambda の zip 形式：依存ライブラリを含めたパッケージの作成が複雑になる。コンテナイメージはローカルの Docker と同じ方法でビルド・確認できる |
| API Gateway の種類 | HTTP API | REST API：費用が高い。WAF・リソースポリシーは BFF 構成では効果が限られる（5.2、5.3） |
| データベース | RDS for PostgreSQL（`db.t4g.micro`、シングルAZ） | Aurora Serverless v2：最小構成でも RDS より高い。マルチAZ：費用が約2倍 |
| VPC 内からの Secrets Manager の利用 | VPC エンドポイント（1AZ） | NAT ゲートウェイ：月45ドル以上。Lambda の環境変数に秘密情報（`Jwt:Key`、DB接続文字列等。AWS のアクセスキーではない）を直接設定：コンソールに値が表示され、Terraform で設定すると state に残る |
| BFF の `SESSION_SECRET` | SSR 実行ロールで Secrets Manager から実行時に読み込む | Amplify の環境変数：実行時に渡すにはビルド時に `.env.production` へ書き出す必要があり、秘密情報がビルド成果物に含まれる |
| IP 単位のレート制限 | 導入しない（リスク受容） | Amplify への WAF：月約21ドル以上（5.2） |
| API への直接アクセスの制限 | 共有の秘密情報のヘッダー | リソースポリシー・IAM 認証（5.3） |
| GitHub Actions の AWS 認証 | OIDC（一時的な認証情報） | アクセスキーを GitHub の Secrets に保存：長期間有効な認証情報が漏洩するリスクがある |
| Terraform の state | ローカル（秘密情報を含めない） | S3：GitHub Actions や複数のPCから Terraform を実行する必要が出た時点で移行する |
| Lambda のアーキテクチャ | x86_64 | arm64（Graviton）：約20%安いが、CI（x86_64）でのイメージのビルドに追加の設定が必要。利用量が少なく差額が小さいため、必要になった時点で切り替える |

# 12. 実装が必要な事項

本書の構成にするため、Terraform のほかに以下の実装が必要である。

| 事項 | 内容 | 関連 |
| --- | --- | --- |
| BFF からの通信の確認 | BFF が `X-Origin-Verify` ヘッダーを付け、API が値を検証する（一致しなければ403） | 5.3 |
| BFF の秘密情報の読み込み | BFF が `BFF_SECRET_ID` のシークレットから `SESSION_SECRET`・`ORIGIN_VERIFY_SECRET` を読み込む（ローカル環境では従来どおり環境変数を使う） | 4.7、4.8 |
| マイグレーション用の処理 | 同じコンテナイメージで、マイグレーションとアプリ用DBユーザーの作成を実行する処理 | 4.3、4.4 |
| Amplify のビルド設定 | `amplify.yml`（モノレポ、Node.js 24、`.env.production` への秘密情報ではない設定値の書き出し） | 4.7 |
| デプロイ用のワークフロー | GitHub Actions でイメージのビルド・ECR へのプッシュ・Lambda の更新（OIDC） | 8章 |
